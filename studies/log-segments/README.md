# Log segments: recovery with several open metadata segments, and the headers freed segments keep

**Status:** read from source, plus a model ([`lanes.py`](lanes.py)) and tests run against `internal/disklog` at `546f956` ([`testdata/stale_header_test.go`](testdata/stale_header_test.go)), with a prototype of the second proposal ([`next-seq.diff`](next-seq.diff)); output in [`results.txt`](results.txt). Both proposals are adopted in the design ([On-disk format](../../docs/design.md#on-disk-format): lanes, `NextSeq` and reuse at once; [Testing strategy](../../docs/design.md#testing-strategy) invariants; [Alternatives considered](../../docs/design.md#alternatives-considered)), with the rebuild rule after cleaning and the C5 rerun with per-worker lanes left as [open questions](../../docs/design.md#roadmap-and-open-questions); the built code is unchanged, and the stale-header tests are the Cleaner item's regression tests.

**Question:** two parts.

1. **Several open metadata segments.** design.md says "Each stream is read from the last of its segments whose first record is at or before the first record to replay", but the metadata stream keeps one open segment per running merge beside the shared one, so a stream is no longer one chain of segments in LSN order. What must recovery read, and from where, so that it finds every record past the replay point at the least reading cost? Merge-step pieces join the index only once a manifest names them: does replay need the merge segments at all?
2. **Freed segments keep this log's header.** A segment the cleaner frees still holds a valid segment header of this log until it is reused. Recovery takes the free segments from the newest manifest's usage table, but a segment opened after that manifest also has a fresh header. How does recovery tell the two apart in every crash order (freed and then the manifest durable, reused before the manifest, TRIM done or not)? The checklist's Cleaner item suggests "the manifest recording the next segment sequence number".

A few terms, for a reader new to log-structured storage:

- A **segment** is a fixed-size piece of the disk (64 MiB on large disks) that the log fills from front to back; its first block is the **segment header**, which names the log, the segment's index on disk, its **stream** (hot, cold or metadata) and its **open sequence number**, a counter the log raises every time it starts filling a segment. A segment that is emptied and filled again gets a new sequence number, so the number names one *use* of the segment.
- A **record** is what one round of group commit writes; its header repeats the log id, the segment's open sequence number and its own block offset, and carries the record's **LSN** (log sequence number), one counter across all streams.
- A **manifest** is a checkpoint written into the log: the sorted runs each index consists of, the **replay LSN** of each index (records after it must be replayed into that index after a crash), and the **segment usage table** as of the manifest's **base LSN** (the newest durable LSN when the checkpoint began): one row per segment that is not free.
- **Replay** reads the records after the oldest replay LSN in LSN order. It stops at the first LSN it cannot find, and the **tail rule** decides whether that gap is the normal end of the log (only rounds that were still in flight are missing) or corruption.

## Summary

**Question 1.** Replay must read the merge segments: their records carry LSNs like any other, and the tail rule needs every LSN past the replay point, or the first missing one reads as a gap with later records behind it, which is corruption. It does not apply their pieces to any index; the manifest names the ones that count. What breaks is the per-stream rule. A merge's segment opens before, and keeps filling after, the shared segments opened later in the same stream, so "the last segment whose first record is at or before the replay point" can be a shared segment opened after the merge segment, and the merge segment's newer records are then never read. In a model of the log, that rule misses a record past the replay point in 74% of crashes with one merge worker and 99% with four; in the code that is usually `Corrupt` at every start, and silent loss when the merge's records are the newest. The built code has two streams of one open segment each, so the rule holds there today; it breaks once merges write segments of their own. Every other log-structured system read here has one sequence per log (F2FS and BSD LFS chain each log through pointers in its blocks and record where each log stood in the checkpoint; NILFS has one log; Pebble and RocksDB number their WAL files and never replay compaction output, which lives outside the WAL). The fix that keeps the design's rule is to make each concurrently open segment its own **lane**: a merge worker's output always goes to that worker's lane, one open segment at a time, the next merge on the worker continuing the segment the last one left, and the segment header names its lane in byte 11, which today is reserved and must be zero. The per-stream rule then holds per lane and never missed a record in the model. Putting merge output back in the shared segment would also keep one chain per stream, but design.md rejects that on the LSM space spike's numbers (30 to 57 segments stranded against 8 to 10). Lanes cost more in group commit than in recovery: a queue, a cursor and the append rule per lane, and turns taken among lanes rather than streams. Replay by lane reads at most one segment per lane before the replay point, about half a segment per lane on average in the model; recording the usage table's newest-LSN column and each open segment's position, F2FS-style, would read half as much but needs more manifest state and still a lane to resume each segment after a restart.

**Question 2.** Recovery today calls every segment whose header is of this log and names its own segment *used* (`internal/disklog/recovery.go:469-475`), whatever the table says. That is design.md's rule and it is correct today, because no built code frees a segment that holds this log's header: only `Format` and `Recovery.Log` mark segments free (`groupcommit.go:378-379`, `recovery.go:1110-1111`). Once the cleaner exists it would go wrong three ways; tests that stage the cleaner's output on disk show each against the committed recovery, and are the regression tests the Cleaner item must pass: a freed segment that kept its header is counted used again at every restart; a reused segment whose new header did not land but whose first record did keeps that record unerased, and a later segment takes its sequence number (harmless while the segment is read under its old header, where the record never decodes, but a hazard once recovery frees the segment, so `NextSeq` and the block-1 rule below must land together); and a segment reused before any segment header names the freeing manifest keeps the old row's live count and adds the new records' blocks to it (7 + 1 = 8 instead of 1). The checklist's suggestion is the right one and is what Pebble and RocksDB do with file numbers: **every manifest records the open sequence number the next segment opened after its base LSN will take**. Recovery loads the newest manifest a durable segment header names, so that is the manifest whose table and `NextSeq` count. A header with a lower number belongs to a segment opened before the base, so the table decides: listed means used or quarantined, absent means free, a stale header. A header at or past it belongs to a segment opened after the base: used, with its row rebuilt from replay. That holds in every crash order, whether TRIM ran or not. Recovery's block-1 rule then counts only a record at or past that number, so the old record a freed segment keeps at block 1 does not make recovery read the segment in full at every start. Reusing a freed segment at once is safe only if the cleaner frees nothing that manifest still needs (its pieces, the runs it names, records after its replay points), which design.md's Cleaning rule already keeps live; that becomes a simulator invariant. The number must be counted from durable rounds only: taken from the log's next sequence when the checkpoint begins, it counts a segment that a round still in flight has opened, and the random-crash property then fails at its first seed. A 64-line prototype passes these tests and every existing test in `internal/`.

## What the design says now

- **Segments and streams** ([On-disk format](../../docs/design.md#on-disk-format)): each stream has its own open segment, and "within it, each running merge fills a segment of its own". The segment header holds "log id, stream, open sequence, newest manifest" (`internal/disklog/segment.go:9-22`, 52 bytes; byte 11 after the stream tag must be zero, `segment.go:101`). Only streams 0 and 1 exist in code (`segment.go:24-31`).
- **Which segments replay reads** (design.md line 224): "Each stream is read from the last of its segments whose first record is at or before the first record to replay." The code does this per stream: it sorts each stream's used segments by sequence number and starts at the last one whose block-1 record is at or before the first LSN to replay (`recovery.go:870-887`), then merges the two streams by LSN (`recovery.go:891-922`). Each stream resumes appending in its newest segment (`recovery.go:1052-1065`).
- **Which segments are free** (design.md line 228): "A segment whose header is of this log and names its own segment is used: the table lists it, or it was opened after the base LSN." A segment whose header reads as zeros or another log's, and which the table leaves out, is free; "its block 1 can still hold the record of a round in flight whose segment header never landed; recovery erases that record and opens later segments with a higher sequence number than it carries". `classify` implements the first rule (`recovery.go:465-482`), `applyTable` takes rows only for listed segments (`recovery.go:638-667`), and replay adds each replayed record's data blocks to its segment's row on top of the table's count (`recovery.go:1003-1008`).
- **The table** is cut when a checkpoint begins: base LSN = the durable LSN then, rows = every segment holding a durable record (`internal/disklog/groupcommit.go:561-571`, `groupcommit.go:758-775`). A round that opens a segment raises the log's next sequence number when it is built, before it is durable (`groupcommit.go:1072-1075`). After recovery the next sequence number is one past the largest any header or found record carries (`recovery.go:1103`).
- **What stays live** (design.md line 251): "A manifest, the snapshot and edits its last piece lists, the runs it names and every record after its replay points stay live until a segment header naming a newer manifest is durable."
- **Nothing frees a segment yet.** The cleaner is not built, so today no crash order can produce a freed segment with a header of this log; the tests here stage what it would leave on disk.
- **The checklist** (Cleaner item): "A segment it frees keeps a header of this log, which recovery takes for one opened after the manifest, so freeing must let recovery tell the two apart, for example by the manifest recording the next segment sequence number." The test scenarios leave both questions open (Metadata stream: "with several open metadata segments, whether that is per segment or per stream"; Cleaner: "how recovery tells them apart").

Two patterns stand out. **Every system keeps one order per log it replays**, and where several logs are written at once (F2FS) the checkpoint records where each one stood and recovery follows each on its own; nowhere does one sequence run across several logs that are open together, as rock-solid's LSN does. The nearest case is Pebble's WAL failover, where one logical WAL is split over several physical files that are written one after another, merged on read with duplicates skipped by sequence number (`wal/reader.go:212-236`, `reader.go:341`). **Every system identifies reuse by a number the checkpoint vouches for, never by what a block says about itself**: Pebble and RocksDB by file numbers below the manifest's next file number, F2FS by checkpoint version, NILFS and BSD LFS by a serial that must continue the checkpoint's. rock-solid's record headers already do the second half, naming the segment's open sequence so a record left from an earlier use never decodes; what is missing is the first half, a number in the manifest against which a segment header can be judged.

## Findings

### 1. The per-stream rule misses records once a stream has two open segments

The model ([`lanes.py`](lanes.py)) writes rounds with global LSNs into a hot, a cold and a shared metadata lane and 0 to 4 merge lanes (64-block segments, a checkpoint every 256 record blocks, each running merge writing a 96-block step while the checkpoint streams, replay points up to 40 records behind the base), stops at a random round and checks, for each rule, whether every record past the newest manifest's replay point lies in a segment the rule reads. It counts reading from where the rule starts in a segment to the segment's end, since replay scans the unused tail of every segment it reads, against the fewest blocks possible: each segment holding a record past the replay point, from its first such record.

| Merge workers | Per stream (design.md now): crashes missing a record | Per lane: missing | Per lane: extra segments read, mean (max) | Usage table + open list + `NextSeq`: extra, mean (max) | Merge lanes skipped: missing |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 of 2,000 | 0 | 1.51 (2.88) | 0.84 (1.89) | 0 |
| 1 | 1,485 | 0 | 2.14 (3.72) | 1.00 (2.58) | 1,361 |
| 2 | 1,837 | 0 | 2.73 (4.69) | 1.12 (3.08) | 1,792 |
| 4 | 1,978 | 0 | 3.98 (6.41) | 1.42 (3.97) | 1,987 |

How the per-stream rule fails: merge segment *M* opens at sequence 10 with its first record at LSN 100 and takes pieces at every checkpoint until it fills; shared metadata segment *S* opens at sequence 11 with LSN 120. With the replay point at 300, *S* is the last metadata segment whose first record is at or before 301, so replay starts there and never reads *M*'s records past 300. Usually that is `Corrupt` at every start while such a merge runs: a missing LSN with later records behind it. When the merge's records are the newest durable ones, as right after a checkpoint has written a step's pieces and before anything else is durable, nothing found lies past the gap, so the tail rule takes the merge's durable records for rounds in flight and drops them. It does not erase them either, since it erases only headers it found, so the log reuses their LSNs: a silent loss at this start and `Corrupt` at a later one that does read the merge segment.

### 2. Replay must read the merge segments, but apply nothing from them

Merge pieces are written by checkpoints (Merge steps: "the next checkpoint ... writes the pieces, the output's root and a manifest edit holding the bounds"), so they take LSNs after the base of the checkpoint that writes them and before its manifest, which puts them past every replay point of that manifest. Skipping merge lanes misses records in 68 to 99% of crashes in the model (last column), for the same reason as above. Pebble and RocksDB can skip their compaction output because it lives in files outside the WAL with no sequence of their own; giving merge records no LSN here would change the record header, the tail rule, blob references (which name an LSN), the usage table's newest column and rebuild, to save at most one step per merge worker of reading per start. Reading only their header blocks and not their data would leave a torn merge record undetected near the tail, accepted as durable, and reported as corruption by a later rebuild that verifies its data. So replay reads merge records whole, as it reads run pieces in the shared segment, and the index owners ignore them; the manifest names the ones that count.

### 3. What recovery must do once the cleaner frees segments

At `546f956` no code path frees a segment that holds this log's header (`groupcommit.go:378-379`, `recovery.go:1110-1111`; a header of this log never classifies as free, `recovery.go:469-477`), so none of these crash orders can happen today. The tests stage what the Cleaner item would leave on disk and fail against the committed recovery, which follows design.md's current rule. They are the regression tests the Cleaner item must pass; no change to the built code is needed before then.

The tests in [`testdata/stale_header_test.go`](testdata/stale_header_test.go) stage on the disk of the existing `usedLog` fixture (60 one-block writes, 16-block segments, checkpoints every 40 blocks) what a cleaner pass would leave on segment 1, whose records all precede the replay point, rewriting the newest manifest in place where needed. Against the committed code all of them fail but the control case ([`results.txt`](results.txt)):

The first would only waste a segment per restart, which the cleaner frees again. The second is harmless under today's rule, since the segment is read under its old header's sequence and the stray record never decodes; it becomes the record with a reused LSN that recovery's erase step exists to remove (design.md: "a later start could find it behind the new tail and replay it") as soon as recovery treats that segment as free, which `NextSeq` does, so the two must land together. The third would make the cleaner misjudge the segment, and live counts could exceed the segment's blocks.

### 4. The next sequence number must come from durable rounds

The table lists what is durable at the base LSN, but a round in flight when the checkpoint begins may already have opened a segment and raised the log's next sequence number (`groupcommit.go:1072-1075`). If the manifest recorded that number, a crash that keeps the round would leave a segment holding durable, possibly acknowledged records whose sequence lies below the manifest's number and which the table does not list: recovery would free it. The prototype records instead one past the sequence of the newest segment a *durable* round opened, kept as rounds retire. Replacing that with the log's next sequence number makes the existing random-crash property fail at seed 1 ("rebuild: log corrupt at LSN 67", [`results.txt`](results.txt)), so the property already guards this.

### 5. Other things found on the way

- **Rebuild after cleaning.** A rebuild replays every record from LSN 1 and stops at the first missing one. Once the cleaner frees a segment (with `NextSeq`, which makes it free and unread) or reuses one (without), rebuild meets LSNs that are gone for good. design.md intends rebuild to "tell a segment the cleaner freed from a damaged one" but gives no rule for the gaps that leaves. Rebuild's chain check has to change, for example to check LSN continuity only past the base LSN and, below it, rely on records in each listed segment following one another block by block, so that a damaged header is still a hole. This study does not settle it.
- **Base or replay point.** design.md line 251 keeps "every record after its replay points" live, but the invariant in Testing strategy (design.md line 1068) and the Cleaner and Invariant checker scenarios (test-scenarios.md lines 1662 and 2029) say "a record after the newest manifest's base". The replay points can lie before the base (an index whose pending write waits), and those records are replayed, so the invariant should say replay points, and "newest manifest" should be the newest one a durable segment header names: "no segment is reused while it holds a live block, or a piece or record that the newest manifest named by a durable segment header needs (a record after its replay points)".
- **TRIM.** A freed segment is free by the table whether or not its TRIM ran, so TRIMs lost at a crash cost nothing but the discard. A TRIM that reads back as ones or garbage instead of zeros makes the header undecodable, which recovery treats as damage and reads in full at every start; the format item's rule (zero the header where a discard does not read back as zeros) is needed for freed segments too. F2FS drops a queued discard for a block it reuses and waits for one already issued (`fs/f2fs/segment.c:1830-1872`, called at `segment.c:3815`), which is the answer the Cleaner scenarios leave open.

## Proposal

### 1. Lanes

- A **lane** is a sequence of segments of one stream that fill one after another: the hot, cold and shared metadata segments are lane 0 of their stream, and merge worker *w* (1 to the disk's merge workers) writes its output to lane *w* of the metadata stream. A lane has at most one open segment. When a merge ends, its worker's segment stays open and the next merge on that worker continues it, which settles what happens to a partly filled merge segment: no tail is left unused behind run pieces the cleaner cannot move. A segment may then hold the tail of one merge's output and the head of the next one's, possibly another index's: at most one such segment per merge boundary. The LSM space spike did not measure that mixing; its C5 model should rerun with per-worker lanes.
- The segment header names its lane in byte 11, today reserved and checked zero (`segment.go:101`), so the header stays 52 bytes. A decoder of the current format rejects a merge-lane header, as it should for a new format; the change rides the version change the metadata stream already needs.
- Recovery groups used segments by (stream, lane) and reads each lane from the last of its segments whose first record is at or before the first record to replay, as it reads each stream today, then merges every lane's records by LSN: a heap of 3 + workers cursors instead of the two heads `pumpReplay` compares. Records of merge lanes count for the LSN chain and the tail rule and are delivered to no index. Each lane resumes in its newest segment.
- Group commit keeps a queue, a cursor and the append rule (`opened`) per lane instead of per stream (`groupcommit.go:342-345`), a round writes one record to one lane, and rounds take the lanes that have work in turn (`groupcommit.go:908-955`). This is most of the change's code.
- Correctness: within a lane, segments are opened one after another and rounds are built in LSN order, so LSNs rise along the lane. Every segment after the starting one has its first record after the first to replay, so all of its records are needed; every segment before it holds only records older than the starting segment's first, which is at or before the first to replay, so none of them are.
- **Cost.** Replay reads at most one segment per lane before the replay point, as it reads one per stream today: with one merge worker, about 2 segments more than strictly needed on average and 4 at most in the model, 128 to 256 MiB at 64 MiB segments, 0.07 to 0.13 s at 2 GB/s. design.md's bound becomes "up to a segment per lane past `max_replay_bytes`", and the checkpoint's own pieces already include its merge steps. Group commit's cost is the per-lane state above and a turn order over 3 + workers lanes.

### 2. `NextSeq` in the manifest

- Every manifest, snapshot or edit, records `NextSeq`: one past the open sequence number of the newest segment a durable round opened, as of its base LSN. Every segment opened by a round after the base gets `NextSeq` or more; every segment opened at or before it got less.
- The manifest that counts is the one recovery loads: the newest that a durable segment header names (`recovery.go:472-474`). A manifest is named only once a later round opens a segment (`groupcommit.go:1114-1115`), so a freeing manifest that is durable but not yet named changes nothing at recovery.
- Recovery, once the manifest is loaded, judges each header of this log that names its own segment:
  - **sequence ≥ `NextSeq`**: opened after the base, used; a row the table holds for it describes an earlier use and is dropped, and replay rebuilds its live blocks and newest LSN.
  - **sequence < `NextSeq`**: the table decides: listed, its row's state; not listed, free, and the header is stale.
- The block-1 rule counts only a record whose sequence is `NextSeq` or more: under a header that reads as zeros or another log's, or under an older header of this log, listed or not, it is the record of a round in flight that opened the segment again and whose header never landed. It is erased, and later segments are numbered past it, as today. An older record at block 1 is left from the segment's earlier use and ignored, so recovery does not read the segment in full at every start; on a disk that is a file, which never TRIMs, every freed segment keeps one.
- Before the first manifest, `NextSeq` is 1 and every header of this log is used, as today; nothing can be freed before a manifest, since every record after the replay points is live.
- **Every crash order:**

| Crash order | Header on disk | Verdict |
| --- | --- | --- |
| Freed in memory, the freeing manifest not durable | Old, sequence < `NextSeq`, listed | Used, as the older manifest's runs may still point into it; replay of the cleaner's copy records moves them |
| Freeing manifest durable, no segment header names it yet | Old, < the loaded (older) manifest's `NextSeq`, listed | Used, with the older manifest's row; the cleaner frees it again |
| A header naming the freeing manifest durable, not reused; TRIM run (zeros) or not | Old, < `NextSeq`, not listed; or zeros | Free |
| As above, TRIM reading back as ones or garbage | Undecodable | Damaged: read in full, free if it holds no record of this log past the replay point (cost: a full read per start until reused, see finding 5) |
| Reused before a header names the freeing manifest, its own header landed | New, ≥ the loaded manifest's `NextSeq` | Used, row from replay |
| Reused after a header names the freeing manifest | New; ≥ `NextSeq` if opened after its base, else listed | Used |
| Reused, the opening round in flight: record landed, header not | Old, < `NextSeq`; not listed, or listed if no header names the freeing manifest yet | The record at block 1, whose sequence is `NextSeq` or more, is erased and later segments are numbered past it; the segment is free, or used under the listing until the cleaner frees it again |
| A segment opened by a round in flight at checkpoint begin, the round kept | New, ≥ `NextSeq` because it counts durable rounds only | Used |

- **Cost.** 8 bytes per manifest and the manifest's format version. The prototype ([`next-seq.diff`](next-seq.diff)) adds 64 lines across `manifest.go`, `groupcommit.go` and `recovery.go`; it handles a stray record under a stale header only when that record's header is one block, which a full version would read through the existing follow pass.
- **Freed segments may be reused at once, under two conditions.** F2FS keeps freed segments *prefree* until the next checkpoint, so that the checkpoint it would recover from never sees them rewritten. rock-solid can reuse at once: a reused segment's header is past the loaded manifest's `NextSeq`, so recovery takes its row from replay, and the cleaner's copy records move whatever the older manifest's runs still map into it. That holds only if (a) the cleaner frees only segments holding nothing the newest manifest named by a durable segment header still needs: its pieces, the runs it names and records after its replay points, which recovery reads by reference before replay starts (`recovery.go:755-837`) and which design.md's Cleaning rule keeps live; and (b) an index's replay LSN never passes a copy record whose moves its runs do not hold, as design.md already says for pending writes (`BeginCheckpoint`'s contract implies it, `groupcommit.go:553`). Measured against the newest *durable* manifest, or against the in-memory index, (a) is not enough. Waiting instead (prefree) would delay freed space until a header names the freeing manifest and remove the reused-before-named crash order, at the price of a state and a wait in allocation.

### Alternatives rejected

| Alternative | Why not |
| --- | --- |
| Q1: the manifest records each open segment and its next block, and replay reads every segment opened after the base, every listed segment whose newest LSN is past the replay point, and each open-at-base segment from its recorded block (F2FS's current segments and offsets) | Reads half of what lanes read (1.0 against 2.1 extra segments at one worker), but needs the open list in every manifest, a k-way merge over segments rather than lanes, and still lanes to know which segment each kind of record resumes in after a restart. Saves about 70 MiB of reading per start at one merge worker. Worth revisiting if restart time measures high |
| Q1: merge output in the shared metadata segment (one chain per stream, today's rule unchanged) | design.md rejects it in "The LSM tree": consumed input pieces died among live flush pieces, and 30 to 57 segments stayed stranded instead of 8 to 10 (LSM space spike, C5) |
| Q1: merge records outside the LSN sequence, as Pebble's and RocksDB's compaction output is outside the WAL | Changes the record header, the tail rule, blob references, the usage table and rebuild, to save at most one step per worker of reading |
| Q1: a lane per merge rather than per worker | An ended merge's last segment would stay a lane head, read at every start until freed, and its unused tail stranded |
| Q2: zero a freed segment's header before the freeing manifest is durable | An extra write ordered before every such manifest; and a zeroed header over an old record at block 1 is exactly what recovery reads in full at every start, so block 1 would need zeroing too. Does nothing for the reused-before-manifest row |
| Q2: an open sequence number in every usage row | 8 bytes per row, up to 2 MiB per snapshot on 262,144 segments, and still nothing for free segments, which have no row |
| Q2: compare the header's first record LSN with the base LSN | Fails when block 1 did not land or is damaged, which is exactly the crash case to handle |
| Q2: F2FS's prefree rule (no reuse until a segment header naming the freeing manifest is durable) | A trade-off, not a necessity: it removes the reused-before-named crash order (`TestStudyReusedSegmentRowComesFromReplay`) but adds a state and a wait to allocation, and still needs `NextSeq` to tell a stale header from a new one. Reuse at once under the two conditions above is chosen |

## What the phase 2 model, the simulator and the tests must check

- **Lanes, as regression tests before the fix:** two merges running with checkpoint flushes, a crash after a step's pieces and before their manifest, and one after it: open recovers every acknowledged record and resumes each lane in its own segment, and no flush piece lands in a merge lane afterwards. With the per-stream rule the same case is `Corrupt`. The many-segments property and the random-crash property run with all three streams and 1 to 4 merge lanes; the trace check counts at most one segment per lane read before the replay point.
- **A lane whose worker is gone** (fewer merge workers configured after a restart): its last segment is read only until the cleaner frees it.
- **Reuse at once:** a simulator invariant that no segment is reused while it holds a piece, run piece or record that the newest manifest named by a durable segment header needs; and a test: segment S holds a run piece M1 names, a cleaner pass ends and M2 is durable but no header names it, so allocation must not hand out S.
- **After recovery** the next open sequence number is at least the loaded manifest's `NextSeq` (it holds because the header naming that manifest was opened after it), checked as a simulator invariant.
- **`NextSeq`:** the tests here become regression tests in the Cleaner and Recovery scenarios, with the crash-order table above as their cases, including TRIM reading zeros and reading ones. A manifest round trip covers `NextSeq` in a snapshot and an edit; the planted bug, `NextSeq` taken when the checkpoint begins, fails the random-crash property (seed 1 in [`results.txt`](results.txt)).
- **Simulator invariant:** after every recovery the usage table equals the log's own, with the cleaner freeing and reusing segments under crashes at every action, extending the random-crash property's existing check.
- **Rebuild after cleaning** needs its own rule and scenarios (finding 5).

## Unverified

- **The model is a model.** It has no cleaner, no freeing and no rounds in flight, 64-block segments, and arbitrary checkpoint, step and replay-lag sizes; it shows which rules miss records and the relative reading, not restart times. The reading figures in MiB scale its segment counts by 64 MiB.
- **The tests stage the cleaner's output by hand**, rewriting the newest manifest's table in place; a manifest edit with a free row, as the real cleaner would write, is not built. The prototype is not a reviewed change, skips a stray record whose header spans blocks, and does not bump the format version, so a manifest of the current format would decode its first index count as `NextSeq`.
- **Lanes were not prototyped** in the code; the model alone supports proposal 1.
- **Rebuild after cleaning** (finding 5) was reasoned, not tested.
- **TRIM that reads back as ones** was not tested.
- **F2FS** was read for its checkpoint layout, roll-forward over the warm node log, the prefree rule and discard waits; how it recovers data logs (`f2fs_recover_fsync_data` past the node chain) was not.
- **The Sprite LFS paper** (Rosenblum and Ousterhout, 1992) was downloaded but not read, since no PDF reader was available; NetBSD's LFS code stands in for its checkpoint and roll-forward.
- **ScyllaDB** was read for leftover sstables at boot and for releasing exhausted inputs; how a restarted incremental compaction picks up its partial output was not.
- **Branch heads, not releases:** Pebble, ScyllaDB and NetBSD were read at their default branches; RocksDB at the local clone's commit; Linux at v6.19. All are pinned in `fetch.sh`.

## Reproduce

- `./run.sh` runs the model, then the tests against a copy of the committed tree (`git archive HEAD`) with the test file added to `internal/disklog`, first as committed, then with `next-seq.diff`, then with the rejected variant; it rewrites `results.txt` in this directory and leaves the rest of the checkout unchanged; the rejected-variant step refuses to run if the diff did not apply. Needs Go 1.27, Python 3 and `patch`; about 30 s.
- `python3 -I lanes.py` runs the model alone.
- `./fetch.sh [dir]` downloads every cited file at the pinned commits into `dir` (default `./work`) and prints the cited lines. Needs `curl`.
