# Block ENOSPC spike

**Question.** When a thin-provisioned block device runs out of space, what does a filesystem on it do if the device fails each write that needs new space with `BLK_STS_NOSPC`, at once or after holding it, or holds the write until the pool grows; and is anything lost? The answer sets what rock-solid's [block frontend](../../docs/design.md#block-frontend) does when a pool is full ([capacity and ENOSPC study](../../studies/capacity-and-enospc/README.md)).

## Setup

The same workload on every device: ext4 made with `lazy_itable_init=0,lazy_journal_init=0,nodiscard` (default `errors=continue`) or XFS made with `mkfs.xfs -K` (no discard) on a 1 GiB device; a 16 MiB file written and `fsync`ed; then a 512 MiB file written and `fsync`ed while the device runs out of space, the 16 MiB file overwritten in place, and the filesystem checked with `e2fsck -fn` or `xfs_repair -n` after unmount.

- **Loop stand-in, [run-loop.sh](run-loop.sh) (T1L, T1D).** Linux 6.18.44 (Firecracker guest `6.18.44-fc-v139`), root, e2fsprogs 1.47.0, no device-mapper. A 1 GiB loop device whose backing file lives on a 192 MiB tmpfs stands in for dm-thin's `error_if_no_space`: a write to a block never written needs a new tmpfs page and fails once the tmpfs is full, and the loop driver completes it with `BLK_STS_NOSPC` ("critical space allocation"), which is what a ublk server returning `-ENOSPC` gives ([`ublk_drv.c`](https://github.com/torvalds/linux/blob/v6.18/drivers/block/ublk_drv.c#L1159), `errno_to_blk_status`). An overwrite of a block written earlier reuses its page. After the big write the run also removes the big file, creates 200 files and writes 4 MiB. T1D mounts with `-o discard`. The tmpfs fails at 4 KiB granularity and cannot hold a write.
- **dm-thin, [run-root.sh](run-root.sh) (T1 to T9).** Bare-metal Linux 6.17.0-1033-oem, Ubuntu 24.04, Intel Core Ultra 5 235U, root, freshly booted; e2fsprogs 1.47.0 and xfsprogs 6.6.0 from Ubuntu; `no_space_timeout` 60 s. A thin pool with 64 KiB blocks and `skip_block_zeroing`, 192 MiB of data space (3,072 blocks) and 16 MiB of metadata, both on loop devices over files, holds one 1 GiB thin volume, so the pool runs out first. `mkfs` provisions the pool blocks it writes: ext4's zeroed inode tables, its 32 MiB journal and, in the same 64 KiB pool block as group 0's, the block bitmaps of every group; XFS's 64 MiB log, AG headers and btree roots and root inode chunk.
  - T1 and T2 refuse at once (`error_if_no_space`) and create 200 files after the big write; T3 to T6 hold (dm-thin's default queue mode); T3 and T4 grow the pool to 1,280 MiB, more than the whole volume, 20 s into the hold; T5 and T6 never grow it.
  - T7 to T9 are XFS runs whose new metadata is written in place while the pool is full: once the big write has filled it, 1,000 files in a new directory (new inode chunks and directory blocks), the directory `fsync`ed to force the log, `vm.drop_caches=2` to push XFS's AIL, then 35 s, past XFS's 30 s log worker, which pushes it too. T7 and T8 refuse the metadata (`error_if_no_space`); T7 then grows the pool and T8 never does. T9 holds it, with the big writer waiting, and grows the pool 19.4 s into the hold.
  - Each test prints its expected outcome before it runs. After a run that fails writes, the pool is grown, the filesystem mounted to replay its log and unmounted, and checked again. The writable probe creates a file. Each test's kernel log and check output are in [results-root2/](results-root2/).
  - Microsoft Defender's `wdavdaemon` scanned the test mounts and appears in the kernel log.
- **An earlier dm-thin run** ([results-root.txt](results-root.txt), kernel log [results-root-kernel.txt](results-root-kernel.txt)) ran T1 to T6 with T3 and T4 growing the pool to only 384 MiB; the run's checks kept no `fsck` output and read `findmnt` for read-only. Its T1, T2, T5 and T6 match the later run; its T3 and T4 are reported below because they show what a grow too small does.

```sh
cd spikes/block-enospc
sudo ./run-loop.sh > results-loop.txt                          # T1L, about 10 s
sudo ID=T1D MOUNT_OPTS=discard ./run-loop.sh >> results-loop.txt
sudo ./run-root.sh | tee results-root2.txt                     # T1 to T9, dm-thin, about 6 minutes
```

`results-root2.txt`'s first line shows `no_space_timeout` and `xfssyncd_centisecs` empty: on a fresh boot `dm_thin_pool` and `xfs` were not yet loaded when it was printed. The script now loads them first; the timeout was 60 s (T5's header line).

## Results

Raw output: [results-loop.txt](results-loop.txt), [results-root2.txt](results-root2.txt) and [results-root2/](results-root2/), [results-root.txt](results-root.txt).

**Loop stand-in, ext4, refused at once.**

| Test | Result |
| --- | --- |
| T1L: ext4, no discard | `fsync` fails with ENOSPC, not EIO; the overwrite succeeds; a 4 MiB write after removing the big file **fails**, since the space ext4 freed never reached the device; `e2fsck -fn` exits 4 (block bitmaps of groups 3 and 5 all zero on disk, free counts and checksums wrong) with the journal still needing recovery |
| T1D: ext4 `-o discard` | The same, except that **the write after `rm` succeeds**; `e2fsck -fn` exits 4 with group 3's bitmap zero on disk and no journal pending |

**dm-thin, ext4 and XFS** ([results-root2.txt](results-root2.txt)). The writer's error is the first one `write()` or `fsync` returned.

| Test | Setup | Result |
| --- | --- | --- |

During the `sync` after the 200 creates, block 32897, the leaf of the big file's extent tree, fails: "lost async page write". **The next create fails with EIO**, which aborts the journal. `e2fsck -fn` exits 4: "Inode 13 has an invalid extent node (blk 32897)", bitmap differences. **After the pool grows, the mount replays the journal and `e2fsck -fn` is clean** |
| T2 | XFS, refused at once | `fsync` ENOSPC; the overwrite, creates and probe succeed. At unmount the first in-place write of the new inode chunk (daddr 0x8100) fails with error 28 and **XFS shuts down** ("Metadata I/O Error (0x1) ... | T4 | XFS, held, grown after 20 s | The same: no error after 20 s, nothing in the kernel log, **`xfs_repair -n` clean** |
| T5 | ext4, held, never grown | ENOSPC after 62 s, when the timeout fails the held writes, block 32897 among them. **The earlier run's T3 and T4** grew the pool from 192 to 384 MiB, less than the 576 MiB or so the run writes. The grow released the held writes with no error, the pool was full again 0.23 s (ext4) and 0.28 s (XFS) later, and the timeout failed the writes 61 s after that: ext4 damaged as in T5, XFS clean as in T6.

Read in the source at [v6.17](https://github.com/torvalds/linux/tree/v6.17) and xfsprogs [v6.6.0](https://git.kernel.org/pub/scm/fs/xfs/xfsprogs-dev.git/tree/?h=v6.6.0):

- **A grow too small restarts the timeout.** dm-thin queues `no_space_timeout` each time the pool enters out-of-data-space in queue mode ([`dm-thin.c:2611-2612`](https://github.com/torvalds/linux/blob/v6.17/drivers/md/dm-thin.c#L2611-L2612)) and cancels it when the pool returns to write mode (`:2616-2617`); the timeout fails the held writes with `BLK_STS_NOSPC` (`do_no_space_timeout`, `:2450-2459`).
- **Overwrites pass dm-thin while it is full.** In out-of-data-space mode a write to a mapped, unshared block is remapped and issued; only writes to unmapped blocks are held or failed (`__process_bio_read_only`, [`dm-thin.c:2026-2055`](https://github.com/torvalds/linux/blob/v6.17/drivers/md/dm-thin.c#L2026-L2055)).
- **Why ext4 stops at the first refused metadata write, with EIO then EROFS.** A failed write of a metadata buffer records an error on the block device's mapping ("lost async page write", [`fs/buffer.c:400`](https://github.com/torvalds/linux/blob/v6.17/fs/buffer.c#L400)). The next handle that asks for write access to a buffer finds that error, aborts the journal and gets EIO ([`fs/jbd2/transaction.c:1222-1231`](https://github.com/torvalds/linux/blob/v6.17/fs/jbd2/transaction.c#L1222-L1231)); in T1 that was the probe's create (`__ext4_new_inode`, [`fs/ext4/ialloc.c:1091-1094`](https://github.com/torvalds/linux/blob/v6.17/fs/ext4/ialloc.c#L1091-L1094)). jbd2 also aborts when it next moves its log tail or unmounts ([`fs/jbd2/journal.c:1861-1864`](https://github.com/torvalds/linux/blob/v6.17/fs/jbd2/journal.c#L1861-L1864), `:2159-2161`). Every handle started after the abort fails with EROFS and puts ext4 in emergency read-only, whatever `errors=` says ([`fs/ext4/ext4_jbd2.c:86-88`](https://github.com/torvalds/linux/blob/v6.17/fs/ext4/ext4_jbd2.c#L86-L88), [`fs/ext4/super.c:722-732`](https://github.com/torvalds/linux/blob/v6.17/fs/ext4/super.c#L722-L732)); that flag does not set `SB_RDONLY`, so `findmnt` keeps showing `rw`. The abort keeps the transactions whose in-place writes failed in the journal, which is why a replay with room repairs the filesystem (T1, T5).
- **Why block 32897.** It is the first free block of group 1, so a block ext4 allocated during the run; T5 creates no files, so its only new metadata is the leaf of the 512 MiB file's extent tree, which needs more than the four extents an inode holds. On dm-thin the bitmaps of new groups share a pool block `mkfs` wrote, unlike on the loop device, where each 4 KiB block is a separate tmpfs page.
- **Why XFS survives a refused metadata write while mounted.** A failed asynchronous metadata write is retried, and `ENOSPC` is retried forever by default ([`xfs_sysfs.c:650-652`](https://github.com/torvalds/linux/blob/v6.17/fs/xfs/xfs_sysfs.c#L650-L652), [`xfs_buf.c:1045-1065`](https://github.com/torvalds/linux/blob/v6.17/fs/xfs/xfs_buf.c#L1045-L1065)): the buffer stays in the AIL marked failed, and every AIL push resubmits it ([`xfs_buf_item.c:599-602`](https://github.com/torvalds/linux/blob/v6.17/fs/xfs/xfs_buf_item.c#L599-L602)), about every 50 ms while the AIL makes no progress ([`xfs_trans_ail.c:605`](https://github.com/torvalds/linux/blob/v6.17/fs/xfs/xfs_trans_ail.c#L605)). The log already holds the change, so nothing above it notices.
- **Why XFS shuts down at unmount.** `fail_at_unmount` is on by default ([`xfs_mount.c:913`](https://github.com/torvalds/linux/blob/v6.17/fs/xfs/xfs_mount.c#L913)) and makes a retried error permanent while unmounting ([`xfs_buf.c:1065`](https://github.com/torvalds/linux/blob/v6.17/fs/xfs/xfs_buf.c#L1065)), which shuts the filesystem down (`:1137`, the line in the T2 and T8 messages) with its log dirty. Log recovery fails at the first refused write (`:1109-1110`), so the replay needs room in the pool.
- **Why XFS stayed clean in T6.** Its only metadata changes were inode 132, in the root inode chunk `mkfs` wrote, and free-space btree roots `mkfs` wrote; the file's few extents fit in the inode. Every refused write was data.
- **Not explained:** T1D, on the loop device, lost group 3's bitmap with no journal pending, which no dm-thin run reproduced; the loop stand-in refuses at 4 KiB granularity and ran Linux 6.18.

## Conclusions

1. **A hold that ends when the pool grows loses nothing.** Held writes complete with no error once the pool has room, and ext4 and XFS check clean, with new metadata among the held writes: ext4's extent leaf in T3, XFS's inode chunks and directory blocks in T9. So rock-solid's block frontend holds writes that need new space for as long as the pool is full.
2. **Failing a write that needs new space stops ext4 at once and loses the refused data.** The first refused metadata write makes jbd2 abort the journal; the next write gets EIO and every later one EROFS, overwrites included, although `errors=continue` and `findmnt` says `rw` (T1, T5). The image left on disk is inconsistent (`e2fsck -fn` exit 4) until a mount replays the journal, and that replay needs the room the pool lacked; with it, the image checked clean (T1, T5). A 60 s hold that ends in failure behaves the same (T5), and a grow too small restarts the hold's timeout (earlier run). So failing needs the same space as holding, plus a remount, and still loses data, which is why rock-solid never fails a held write unless an operator asks.
3. **XFS survives a refused write while it stays mounted, and not at unmount.** It retries refused metadata forever, keeps serving writes, and checks clean once the pool grows (T7). Unmounted with the pool still full, it shuts down, and its image needs a log replay with room (T2, T8). A pod is deleted, or its node drained, regardless of the pool, so XFS needs the hold as much as ext4.
4. **ENOSPC, not EIO, reaches `fsync`** on both filesystems (T1, T2, T5 to T8), and dm-thin passes overwrites of provisioned, unshared blocks while it is full (T1, T2, T6), so letting overwrites past `write_limit` is right: the journal and every block the filesystem already wrote keep working while new allocation waits. ext4 stops using them only after a refused write (T5).
5. **Without discard, deleting files frees nothing in the pool** (T1L): a full pool stays full after the application cleans up. With `-o discard` the space came back at once (T1D). The CSI driver mounts the filesystems it creates on block volumes with `discard`.
