# SPDK NVMe interrupt-mode spike

**Question.** Does SPDK's PCIe NVMe driver support interrupt mode, where completions arrive as MSI-X interrupts through `vfio-pci` on an eventfd so the SPDK thread can sleep in `epoll` instead of busy-polling? What does it cost in latency and CPU compared with poll mode? The answer decides whether the opt-in SPDK disk driver can follow the driver contract from [bypass-drivers](../bypass-drivers/) (readiness fd, event mode by default) on real NVMe, or must own a busy-polled core.

**Setup.** Linux 6.17 (`6.17.0-1033-oem`), Intel Core Ultra 5 235U laptop. Its IOMMU has a 42-bit address width and interrupt remapping. The only NVMe drive is the root disk (`0000:05:00.0`), so it is never touched. SPDK v26.09 with DPDK 26.03 is a separate shallow clone built with `--with-vfio-user` and the apps; the dev-header sysroot is reused read-only from `../bypass-drivers`. QEMU 8.2.2 comes from Ubuntu `.deb`s. `/dev/kvm` is usable by uid 1000 through an ACL. No host root is used. One harness, `nvme_intr.c`, drives the NVMe driver in two ways: raw `spdk_nvme` (a poll group whose fd sits in our own `epoll`), and `bdev_nvme` inside one `spdk_thread` (as in bypass-drivers).

Stand-ins and what they can't settle:

- **I2, vfio-user** (host, as a normal user): SPDK's nvmf target exports a malloc bdev as an emulated NVMe controller over a UNIX socket, and SPDK's own initiator connects to it. It shares `nvme_pcie_common.c` (queues, PRPs, doorbells, completion handling) with real PCIe. It has no MSI-X, no IOMMU and no `vtophys`, so it can't show interrupt behaviour at all.
- **I3, QEMU/KVM guest**: the host kernel and an initramfs boot under `-device nvme,ioeventfd=on`, with `q35,kernel-irqchip=split` and `intel-iommu,intremap=on` (39-bit vIOMMU), or without a vIOMMU using vfio no-IOMMU mode. The guest is root inside the VM. This tests the real PCIe driver path: vfio-pci, MSI-X, eventfds and the IOMMU. **The emulated device's latency (35 to 120 µs at QD1, varying 3× between boots) and the guest's CPU numbers (every doorbell, MSI and EOI is a VM exit charged to the guest) are not real NVMe numbers.** They show direction, not size.

```
../bypass-drivers/fetch.sh        # once: dev-header sysroot (this spike only reads it)
./fetch.sh                        # SPDK v26.09 + libvfio-user build, QEMU and guest kernel .debs (no root)
./build.sh                        # bin/nvme_intr
./run-vfiouser.sh                 # I2  -> results-vfiouser.txt
./run-qemu.sh iommu [tag]         # I3  -> results-qemu-iommu[-tag].txt  (needs rw /dev/kvm)
./run-qemu.sh noiommu             # I3  -> results-qemu-noiommu.txt
# I4, real spare NVMe (root; refuses the root disk and anything mounted):
sudo ./setup-root.sh 0000:XX:00.0 --wipe-ok && sudo ./run-real.sh 0000:XX:00.0 && sudo ./teardown-root.sh 0000:XX:00.0
```

## I2: vfio-user stand-in (host, uid 1000, no hugepages)

Target `nvmf_tgt --no-huge` on core 1, initiator on core 0, malloc bdev, 4K, 20,000 writes + 20,000 reads.

| Test | Result |
| --- | --- |
| V1: poll mode | Attach ok, 127 I/O queues, no qpair fd (`-EOPNOTSUPP`). QD1 write/read p50 1.2 / 1.1 µs, 1.2 µs of initiator CPU per I/O, 100% of a core idle. QD32 1.16 M IOPS at 0.86 µs CPU per I/O. `spdk_vtophys` fails on DMA buffers yet I/O works, because vfio-user uses the virtual address as IOVA ([nvme_pcie_common.c:27-36](https://github.com/spdk/spdk/blob/v26.09/lib/nvme/nvme_pcie_common.c#L27-L36)) |
| V2: `enable_interrupts=1` | **Attach succeeds; `opts.enable_interrupts` reads back 0** ("Failed to enable interrupts!", `nvme_ctrlr.c:3235`), as I1b and I1f predict. The harness notices it and runs in poll mode, with the same numbers as V1 |
| V3: trust the request and sleep on the fd | **Hangs**: the fd group is empty, `epoll_wait` returns EINVAL once a second, and no I/O completes until the 5 s kill |
| V4: `bdev_nvme`, poll thread | QD1 p50 1.4 / 1.2 µs, 1.4 µs CPU per I/O |
| V5: `bdev_nvme`, interrupt thread | `spdk_bdev_nvme_create` → `-EOPNOTSUPP` (I1f) |

What carries over to PCIe: the software cost of the shared submit/complete path (about 1 µs and 1 µs of CPU per 4K I/O), and the fallback behaviour. What doesn't: everything about interrupts, IOMMU mapping and `vtophys`.

## I4: what a real-NVMe measurement needs

| Item | Status |
| --- | --- |
| Hardware | A **spare** NVMe controller (M.2 or U.2, or a USB4/Thunderbolt NVMe enclosure, which shows up as PCIe) whose IOMMU group holds nothing else bound to a driver. Its data in the first 256 MB is overwritten |
| Root, once | `setup-root.sh <BDF> --wipe-ok`: refuses non-NVMe devices, the root disk's controller and any controller behind a mounted filesystem, swap or dm/md/LVM holder (checked as uid 1000: it refuses `0000:05:00.0`). Then it unbinds `nvme`, binds `vfio-pci` via `driver_override`, and reserves 512 × 2 MB hugepages. `teardown-root.sh` restores the original driver |
| Root to run | Hugepage mode on this laptop is IOVA=PA (G8), so `run-real.sh` runs as root. Untested alternative: a user who owns `/dev/vfio/<group>`, with `RLIMIT_MEMLOCK` ≥ the DMA pool, in no-huge mode with ≤ ~250 MB of DMA memory (G7) |
| IOMMU | VT-d on with interrupt remapping. This laptop has both (ecap IR=1, MGAW 42). Without interrupt remapping vfio type1 refuses the group unless `allow_unsafe_interrupts=1` ([vfio_iommu_type1.c:2234](https://github.com/torvalds/linux/blob/v6.17/drivers/vfio/vfio_iommu_type1.c#L2234)) |
| Measure | `run-real.sh` repeats G1 to G7 plus `spdk_nvme_perf` at QD 1/32/128 with and without `-E`, and records the CPU idle states (C-state exit latency is the expected extra cost of sleeping) → `results-real.txt` |

## Conclusions

1. **Interrupt mode works on PCIe NVMe through vfio-pci, so the SPDK driver follows the same contract as the other drivers: one readiness fd, event mode by default.** Each I/O qpair gets its own MSI-X vector and eventfd, and the poll group's `spdk_fd_group` fd sits in our epoll (tokio `AsyncFd`). The KVM guest saw 1.00 interrupts and 1.00 wakeups per QD1 I/O, 0.1% CPU idle (poll: 100%), and less CPU per I/O: 2.7 to 4.5× at QD1 and 3 to 4× at QD32 in `nvme_intr`, 1.3 to 1.6× at QD1 and 3.3 to 4.4× at QD32 in `spdk_nvme_perf`. It works with the IOMMU and in vfio no-IOMMU mode. It does not work with `uio_pci_generic`, so the driver requires vfio-pci.
2. **The driver checks the mode after attach and never trusts the request.** SPDK resets `enable_interrupts` to false, logs one line, and attaches in poll mode whenever interrupts can't be enabled (uio, vfio-user, TCP, no MSI-X). A loop that then sleeps on the fd hangs forever (V3). Read `spdk_nvme_ctrlr_get_opts()->enable_interrupts` after attach. On a mismatch, either fail the disk with a clear error or switch it to a busy-polled core on purpose, and report the mode at startup.
3. **Event mode is limited to PCIe for local disks (and RDMA if NVMe-oF ever matters).** The vfio-user and TCP initiators have no interrupt support, and `bdev_nvme` refuses them in interrupt mode. The admin queue has its own fd (AERs, admin completions) and must be registered too, as `bdev_nvme` does. Qpairs are created synchronously, with no `delay_cmd_submit` and no SPDK multi-process.
4. **DMA memory sizing is part of the driver config.** With an IOMMU, SPDK runs without hugepages (IOVA=VA), but vfio's 65,535-mapping limit caps no-huge DMA memory just under 256 MB (128 MB works, 256 MB fails with ENOSPC). Raising it needs the root-only `vfio_iommu_type1 dma_entry_limit` parameter. With hugepages, an Intel IOMMU narrower than 48 bits (this laptop: 42) makes SPDK use IOVA=PA, which needs root. No-IOMMU mode needs hugepages and PA. So the driver-owned buffer pool (bypass-drivers conclusion 1) gets an explicit size, defaulting to ≤ 128 MB in no-huge mode and switching to hugepages above that.
5. **Interrupt latency on real NVMe is still open; CPU savings are not.** Every stand-in agrees on direction: interrupt mode adds a few µs at QD1 (KVM guest: −1 to +21 µs on a 37 to 122 µs p50, and `spdk_nvme_perf` +8 to +13 µs average; bypass-drivers S4 measured the epoll/eventfd wake path alone at +1.4 µs) and cuts CPU per I/O several times. Emulated device latency varies 3× between boots, though, and VM exits inflate guest CPU, so neither number transfers to hardware. Keep event mode as the default and busy-poll as the opt-in for dedicated cores, and take the real numbers from `run-real.sh` on a spare drive before the SPDK driver lands (roadmap phase 9).
6. **High queue depth relies on the device's coalescing, not SPDK's.** SPDK never sets NVMe Interrupt Coalescing. The emulated device batched about 30 completions per interrupt at QD32, but a real drive may interrupt per completion. The real-drive run must report interrupts per I/O at QD32 and QD128 to show whether the driver should set the coalescing feature.
