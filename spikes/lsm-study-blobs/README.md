# Value separation spike

**Question.** Our disk log is value separation: chunk data stays in the log, the chunk index maps each extent to its location, and a cleaner copies live blocks out of victim segments and changes the index ([On-disk format](../../docs/design.md#on-disk-format)). WiscKey, RocksDB's integrated BlobDB, Titan and Pebble all separate values the same way. How do they get a relocated value's new location to readers: by writing the index once per moved value, as our cleaner's moves do (42 to 72 ns each on the index's owner), by relocating values only when a compaction rewrites their index entries anyway (RocksDB), or through a forwarding table that the cleaner updates instead of the index (Pebble's blob file rewrite)? Which of these suits an in-memory, zero-allocation chunk index where the cleaner's moves cause 55 to 92% of the index's entries? And two open questions: how should a rebuild apply a cleaner's copy of a block that a later write replaced, and does any engine separate its cleaner output by temperature?

**Setup.** Source reading, plus a small simulation of index writes per moved block.

- **Sources.** Pebble master at [`a7b8321871e3`](https://github.com/cockroachdb/pebble/tree/a7b8321871e3e3c19be21eaf42a6aaa7e2d04f23) (2026-10-14); RocksDB [`v11.8.1`](https://github.com/facebook/rocksdb/tree/v11.8.1); Titan master at [`b21afb5d7a50`](https://github.com/tikv/titan/tree/b21afb5d7a50f960fbf47a19c103ebc6c43636a3) (2026-04-28); WiscKey, Lu et al., [FAST 2016](https://www.usenix.org/conference/fast16/technical-sessions/presentation/lu), §3.3. [fetch.sh](fetch.sh) fetches the three trees at those refs into `work/src`. Citations below are `file:line` in those trees.
- **Simulation.** [sim/main.go](sim/main.go), Go 1.27, no dependencies, deterministic (seeded PCG). An 8 GiB stand-in disk of 2,048 segments of 1,024 4K blocks, 4 MiB chunks, 256-block records, 8 free segments kept, cost-benefit victim choice with the age capped at one disk capacity, 4 victims per pass, as in the [cleaner streams spike](../cleaner-streams/). The disk is filled with whole chunks, then takes 4 capacities of random 4K overwrites to warm up and 2 to measure; `uniform` or `hc90` (90% of writes to 10% of chunks), at 80, 90 and 95% full. Header blocks and metadata are not modelled, so write amplification (WA) is the header-free model's. Three index models run side by side over the same cleaning:
  - **D**, the design and `chunkstore.(*Index).Move`: each move run (consecutive blocks of one chunk in one extent, copied to consecutive locations of one record) puts the moved extent plus the left and right remainders it splits off, and changes two record counts.
  - **DC**, D plus coalescing: a moved run joins the extent before it when that extent ends at the block before, in the same copy record and at the location before.
  - **F**, a forwarding table keyed by original address, the index never touched by a move. Two granularities: per block run (an entry per run consecutive in original address and in destination), and per original record, as Pebble remaps a rewritten blob file (an entry per pair of original record and destination record, the record's surviving blocks found by their rank, as Pebble keeps a value's position).
  - Copy order `chunk` (the design: a pass's live blocks grouped by chunk) or `origin` (by original address, as a Pebble rewrite keeps a file's order).

```
./fetch.sh                  # sources into work/src (read-only references)
./run.sh                    # 12 runs into results.txt, about 40 min on 4 shared vCPUs
go build -o bin/blobsim ./sim && bin/blobsim -wl uniform -u 0.9 -order chunk   # one run
```

Raw output: [results.txt](results.txt).

## Findings per engine

### How a relocated value reaches readers

| Engine | Mechanism | Citation |
| --- | --- | --- |
| WiscKey | GC reads a chunk from the vLog's tail, checks each value's validity with an LSM lookup (the vLog stores the key with the value), appends valid values at the head, `fsync`s the vLog, then writes each new address and the new tail into the LSM tree synchronously, and only then frees the space. **One index write per relocated value.** | FAST 2016, §3.3.2 |
| Titan GC | Reads a blob file, keeps the blobs whose key still holds this blob index (`DiscardEntry`, one LSM `Get` per key), writes them to new blob files, installs those in its manifest, then writes each key's new blob index through the normal write path with a `WriteCallback` that rejects it when the key no longer holds the old blob index, and deletes the inputs last. **One index write per relocated value, applied only if the index still points at the copied blob**, as our owner applies a move. | `src/blob_gc_job.cc:15-60` (callback), `347-381` (`DiscardEntry`), `383-410` (install, rewrite, delete), `488-540` (`RewriteValidKeyToLSM`) |
| Titan level merge | Optional (`level_merge`, default off): values are rewritten into new blob files when their keys are compacted into the last two levels, so the new index entry rides on the compaction. Documented to cost about 3 more write amplification on uniform keys; `range_merge` then caps sorted runs of blob files per range (`max_sorted_runs` 20). | `include/titan/options.h:125-157` |
| RocksDB BlobDB | GC happens only inside compaction: a blob reference into a file older than the cutoff (the oldest `blob_garbage_collection_age_cutoff` = 25% of blob files) is fetched and written to the compaction's new blob file, and the new reference goes into the output SST the compaction writes anyway. **No extra index write**, but relocation follows key-range compaction, not garbage. `blob_garbage_collection_force_threshold` (default 1.0, off) schedules compactions of the SSTs that reference the oldest files when their garbage ratio passes it. `enable_blob_garbage_collection` defaults to false. | `db/compaction/compaction_iterator.cc:1425-1493`, `2012`; `db/version_set.cc:3855-3900`; `include/rocksdb/advanced_options.h:1122-1157` |
| Pebble | A *blob file rewrite* compaction copies a blob file's referenced values into a new physical file **without rewriting the sstables that reference it**. References name `(blob file ID, block ID, value ID)`; the version maps the stable file ID to its current physical file (`BlobFileMetadata{FileID, Physical}`), and the rewritten file's index block carries a *virtual blocks* column, 8 bytes per original block, mapping each old block ID to a physical block and a value-ID offset. Dropped values stay as empty slots so positions survive. Liveness comes from per-sstable bitmaps of referenced values per blob block, unioned at rewrite time. The read path costs nothing extra: the file-ID lookup is an in-memory B-tree, and the remap sits in the index block a blob read loads anyway. | `sstable/blob/doc.go:25-90`; `internal/manifest/blob_metadata.go:28-97`, `407-430`; `blob_rewrite.go:80-86`, `364-377`; `sstable/blob/blocks.go:188-202`; `sstable/blob/fetcher.go:298-313`; `sstable/blob_reference_index.go:143-156` |
| Pebble compactions | A compaction preserves blob references by default and writes values to new blob files only when an output sstable would reference more than `MaxBlobReferenceDepth` (10) overlapping blob files, to restore read locality. | `compaction_value_separation.go:80-117`; `options.go:1316-1323` |

Why Pebble needs the indirection: its references live in immutable on-disk sstables, so changing one reference means rewriting a whole sstable, possibly on shared storage. Ours live in an in-memory memtable, where a move is one put.

### What to separate, when to clean, how garbage is counted

| Practice | Pebble | RocksDB | Titan / WiscKey |
| --- | --- | --- | --- |
| Separation threshold | `MinimumSize` 256 B, 1 KiB for likely MVCC garbage; per-span overrides (`options.go:1302-1315`, `1684-1695`) | `min_blob_size` (0 by default, the user sets it) (`advanced_options.h:1094`); `blob_file_starting_level` delays separation for short-lived values (`:1166-1179`) | Titan `min_blob_size` 4 KiB (`options.h:77-81`); WiscKey separates every value |
| Victim choice | Lowest referenced ratio first (`blob_metadata.go:1029-1035`), only files older than `RewriteMinimumAge` 5 min (`:993-1004`), one rewrite at a time; scheduled at low priority once 10% of blob bytes are garbage and at high priority past 20% (`compaction_picker.go:1756-1812`) | The oldest 25% of blob files, during compaction | Titan: discardable ratio ≥ 0.5, batches of 512 MiB to 1 GiB, small files merged (`options.h:104-122`, `blob_gc_picker.cc:33-43`); WiscKey: the tail, first in first out |
| Garbage accounting | Each sstable's `BlobReference.ValueSize`, summed per blob file (`blob_metadata.go:28-49`) | `BlobFileAddition` (total count and bytes) and `BlobFileGarbage` (garbage added) in each VersionEdit, from a compaction's inflow minus outflow per blob file (`db/blob/blob_file_addition.h:22-34`, `blob_file_garbage.h:21-33`, `blob_garbage_meter.h:22-27`); a file is dropped once no SST links it and its garbage reaches its total (`db/version_builder.cc:1604-1607`) | Titan: `live_data_size` per blob file, updated from compactions (`src/blob_format.h:268-276`) |
| Freeing order | Rewrite installs the remapped file in one version edit, after checking the file was not rewritten meanwhile (`blob_rewrite.go:203-235`) | Version edit | Titan: new files in the manifest, then keys, then delete inputs (`blob_gc_job.cc:383-410`); WiscKey: `fsync` copies, then index and tail, then free |
| Caching | Rewrites read through a private buffer pool, never the block cache, since readers move to the new file (`blob_rewrite.go:314-320`) | `blob_cache`, separate or shared with the block cache; `prepopulate_blob_cache` on flush (`advanced_options.h:1181-1200`) | Titan `blob_cache` (`options.h:99-102`) |
| Temperature | Experimental tiering by a per-span attribute; blob references are all written to the hot tier so far (`options.go:877-882`, `valsep/value_separator.go:41`) | `last_level_temperature`, `preclude_last_level_data_seconds` (data younger than this kept out of the last level, from a sampled sequence-number-to-time map) and per-key placement into the proximal level, all experimental and for a cold device tier (`advanced_options.h:1005-1068`, `db/compaction/compaction.h:388-392`) | None |

No engine separates its GC output by temperature. RocksDB's and Pebble's temperatures place data on a cheaper device by age or by an attribute the application supplies; they do not aim to lower GC write amplification.

## Conclusions

1. **Keep updating the index once per move, applied by the index's owner only where a map still stores the copied blocks at the copy's source.** WiscKey and Titan's GC do the same, Titan with the same check (`blob_gc_job.cc:15-60`). A move costs one extent put (M1), 42 to 72 ns on the owner, and about 40 B of index entry per 4 KiB moved; the cleaner streams spike put all index runs at about 6% of the bytes written at 90% full, so a forwarding table could save at most about 5%.
2. **Do not adopt Pebble's blob-file mapping.** Pebble needs it because its references sit in immutable on-disk sstables and its read already loads the blob file's index block that holds the remap; ours sit in an in-memory memtable and a read goes straight from extent to location. Its best form here, a remap per original record (M4), writes 19 to 33× fewer index entries but puts an extra lookup on 63 to 96% of reads (M6), needs copies in original order, which costs hc90 6 to 7% more WA (M5), needs index entries to name a record by a stable identifier instead of its location, and adds a table every checkpoint and rebuild must carry. A remap per block run saves nothing (M3).
3. **Do not relocate during compaction, as RocksDB does.** Our size-tiered compaction merges runs over the whole key space; the entries of the oldest data sit in the largest run, which merges only after three more runs of its class, so forcing relocation (RocksDB's `force_threshold`) means rewriting the whole index, over 10 GB for a 1 TB block-volume disk. Relocation would also follow key ranges instead of free space, where cost-benefit wrote 36 to 45% less than greedy on skewed overwrites. RocksDB ships it off by default, and Titan documents about 3 more WA on uniform keys for its level merge.
4. **A copy entry names the location it copied from, and replay applies it with the owner's check.** Titan's GC writes go through the write-ahead log after their check, so replay in log order repeats them. Ours are logged before the owner checks, so a copy logged after a write that replaced its block must be skipped: the source location tells, the same test `chunkstore.(*Index).Move` makes live. A record with only single-block copies of 256 blocks still needs 3 header blocks with 8 more bytes per entry.
5. **The cleaner does not regroup chunks overwritten at random** (M2). Pebble rewrites values into new blob files when an sstable would reference more than 10 blob files, and Titan merges blob files past 20 sorted runs per range: both bound fragmentation with a rewrite of their own, not with GC.
6. **No engine separates GC output by temperature.** RocksDB's and Pebble's temperatures place data on a cheaper device; our pools do that. Two streams stay.
7. **Cleaner reads skip the cache**, as Pebble's rewrites read through a private buffer pool (`blob_rewrite.go:314-320`): once the moves apply, readers go to the copies.
