# FUSE daemon restart spike

**Question.** Can the FUSE daemon restart or upgrade without breaking mounts by handing its `/dev/fuse` file descriptors to the new process, or do we need one mount process per volume (as JuiceFS does with mount pods)? This answers the open question in [docs/design.md](../../docs/design.md) under "Daemon restart and upgrade": what happens to requests the old daemon read but never answered, whether `FUSE_NOTIFY_RESEND` requeues them, and where the descriptors live while no daemon runs.

## Setup

- Linux 6.17.0-1033-oem (Ubuntu OEM build), x86_64, 14 cores, Ubuntu 24.04 desktop session. Kernel sources cited at the upstream `v6.17` tag.
- libfuse 3.18.3, built twice from a shallow clone: the default build and one with `-Denable-custom-io=true`. The host's `fusermount3` is 3.14.0 (setuid). systemd 255 user manager.
- `rawfs.c` speaks the `/dev/fuse` protocol by hand (v6.17 uapi header) so that nothing hides what the kernel does. It is a flat passthrough of one backing directory with nodeid = backing `st_ino` and fh = nodeid. A successor can therefore rebuild every handle from the backing directory alone (it logs `RESCAN` when it does). It mounts through `fusermount3`, and it can hand its fds over in four ways: `SCM_RIGHTS` to a waiting successor, `execve` of itself, a separate fd-holder process (`rawfs hold`), or the systemd fdstore. With `--hang` it reads some requests and never answers them.
- `llfs.c` is the same filesystem written against the libfuse 3.18 low-level API. It is used to check what libfuse allows on an fd that the kernel already INITed, and as the one-process-per-mount baseline for memory.
- `run.py` drives each scenario with a separate client process, so a hung syscall cannot hang the harness. Each scenario prints its expected outcome before it runs. It reads `/sys/fs/fuse/connections/N/waiting`, and on exit it aborts every connection through fusectl, unmounts, and kills its processes and systemd units.
- **Stand-ins and limits.** The only setup tested was an unprivileged user mount without `allow_other` (`user_allow_other` is off in `/etc/fuse.conf`). Nothing ran as root, in containers, or across mount namespaces; unprivileged user namespaces are restricted by AppArmor here. The machine was shared with other agents and runs a GNOME session, whose mount monitors (`gvfs-udisks2-volume-monitor`, `gnome-system-monitor`) probe every new mount. That probing explains the extra `waiting` request in F6a and the occasional EBUSY on unmount. The F6b control run with no handoff shows a scheduling noise floor of 5–9 ms for the longest stat in a 1.2 s loop.

```sh
cd spikes/fuse-restart
./fetch.sh          # libfuse fuse-3.18.3, linux v6.17 fs/fuse + uapi header, fusermount 3.14 source, meson/ninja via pip --target
./build.sh          # bin/rawfs, bin/llfs (custom-io libfuse), bin/llfs-default
python3 run.py | tee results.txt          # all scenarios (~3 min); or: python3 run.py F1 F5
```

## Results

Raw output: [results.txt](results.txt). All 86 checks passed in the recorded run. F9a/F9b/F9c replace a first F9 whose expected outcome was wrong; see F9a.

| Test | Result |
| --- | --- |
| F1 SCM_RIGHTS handoff, A exits | **The mount survives. A file opened under A reads and writes through B, a fresh open and `readdir` work, and B saw 0 INITs. B rebuilt its nodeid table from the backing directory (1 `RESCAN`). Handoff took 276 µs from A's send to B ready.** |
| F2 request A read, never answered, A exits after handoff | The caller stays blocked (still blocked after 2 s; fusectl `waiting=1`). Other requests are served by B. The request sits on the processing list of the `fuse_dev` that B now owns, and nothing times it out by default. |
| F2b same, without `FUSE_PARALLEL_DIROPS` | The hung LOOKUP holds the parent's `fuse_inode` mutex ([`fuse_lock_inode`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/inode.c#L589)), so a stat of another name in the same directory hangs too, until B resends. |
| F3 B sends `FUSE_NOTIFY_RESEND` | The hung LOOKUP is requeued with unique `0x14a` → `0x800000000000014a` (bit 63 = `FUSE_UNIQUE_RESEND`). B answers it, and the caller returns 581 µs after the notify. The kernel offered `FUSE_HAS_RESEND` in INIT, but A never acknowledged it: the notify is not gated on negotiation ([`fuse_notify_resend`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L2028)). libfuse 3.18.3 has no call that sends this notify (only the constants in `fuse_kernel.h`), so it is a 16-byte write by hand. |
| F3c B replies with bit 63 cleared | The reply is rejected with ENOENT and the caller stays blocked: [`fuse_request_find`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L2085) compares the full unique. |
| F3b RESEND of a MKDIR that A had applied | **The caller's own `mkdir` fails with EEXIST.** B re-executed it. RESEND is only safe for idempotent requests, as the [`fuse_resend`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L1970-L1982) comment says. |
| F4a last fd closed (exit, no handoff) | The next request gets ENOTCONN, and the mount entry stays until it is unmounted. |
| F4b SIGKILL with a request read but unanswered, no other holder | The hung caller gets ECONNABORTED and later callers get ENOTCONN. [`fuse_dev_release`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L2489-L2516) ends that fd's processing list with `-ECONNABORTED` ([`fuse_dev_end_requests`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L2361)). On the last `fuse_dev` it calls [`fuse_abort_conn`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L2406), after which new requests fail with `-ENOTCONN` ([`fuse_dev_queue_req`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L372-L386)). |
| F4c A reads on a `FUSE_DEV_IOC_CLONE` fd and hands off only the original | The mount survives, but the request read on the dropped clone gets ECONNABORTED. Requests read on a clone are on that clone's own processing list, which is ended when its last reference closes. |
| F4d hand off the original and the clone, then RESEND | B received 2 fds and the caller succeeds. |
| F5a fd-holder process, A crashes (SIGKILL) with a request in flight, B started cold | The mount survives the crash. B gets the fd from the holder and resends, and the hung caller succeeds. The holder sees `POLLERR` on the fd at unmount and drops it ([`fuse_dev_poll`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L2338)). |
| F5b re-exec in place (`execve`, fd without `O_CLOEXEC`) | Same PID; the old handle still reads; 0 INITs; 1.6 ms from exec to serving. |
| F5c systemd `--user` fdstore (`FDSTORE=1` for the fuse fd plus a memfd holding the INIT state) | Works as an unprivileged user. Both `systemctl --user restart` and SIGKILL with `Restart=always` hand back `LISTEN_FDS=2 LISTEN_FDNAMES=state:fuse`, the old handle keeps reading, and there was 1 INIT across both restarts. `systemctl stop` flushes the store, and the mount then gives ENOTCONN. |
| F6a request issued while only the holder has the fd, B started 500 ms later | It blocks for the gap (441 ms) and then succeeds; returns 5 ms after B's exec. |
| F6b stat loop across each handoff, 5 runs each, median | No errors in any of the 30 runs. Stall of the stat that overlaps the handoff: hot standby over SCM_RIGHTS 0.68 ms (daemon-side gap 0.38 ms); re-exec 1.7 ms (1.5 ms); cold start from the holder after SIGKILL 4.2 ms (3.8 ms); `systemctl restart` 21 ms; systemd SIGKILL + restart 27 ms. The control with no handoff: 0 ms. |
| F7 cost of one libfuse process per mount, 10 mounts | Single-threaded loop: 10 processes, 21.5 MB RSS, but only 2.3 MB PSS (about 230 kB each, the rest shared libc), 10 threads. `loop_mt`: 3.5 MB PSS and 43–47 threads. One process with 10 sessions: 2.7 MB RSS, 1.0 MB PSS, 11 threads. |
| F8 `request_timeout=15` negotiated (`FUSE_REQUEST_TIMEOUT`, 6.14+), request left unanswered after handoff | The kernel aborted the whole connection after 30.3 s although B held the fd. The checker runs every 15 s (`FUSE_TIMEOUT_TIMER_FREQ`), so the abort comes 15–30 s after the request. The hung caller got ECONNABORTED, then ENOTCONN, and B's read gave ENODEV ([`fuse_check_timeout`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L74)). The same abort applies if the host sets `fs.fuse.max_request_timeout` or `default_request_timeout` ([`init_server_timeout`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/inode.c#L1280)); both are 0 here. |
| F9a `-o auto_unmount`, A killed, no handoff (control) | The dead mount is left in place. My first expectation, that fusermount3 would unmount, was wrong. fusermount3 3.14 unmounts only if its `open(mnt)` probe gets ENOTCONN ([`should_auto_unmount`](https://github.com/libfuse/libfuse/blob/fuse-3.14.0/util/fusermount.c#L1201)). The probe runs with euid 0, and on a mount without `allow_other` the kernel denies root ([`fuse_permissible_uidgid`](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dir.c#L1463)), so the probe gets EACCES. |
| F9b auto_unmount, hand off only the fuse fd | The mount survives. fusermount3 sees its socket close when A exits and quits, so nothing watches B any more. |
| F9c auto_unmount, hand off the fuse fd and the fusermount3 socket | The mount survives. fusermount3 stays alive, tied to B, and exits when B dies. Whether it then unmounts could not be seen here (see F9a). |
| L1 libfuse on an already-INITed fd through the `/dev/fd/N` mountpoint | Every request gets EIO. libfuse waits for an INIT that never comes ([`fuse_req_opcode_sanity_ok`](https://github.com/libfuse/libfuse/blob/fuse-3.18.3/lib/fuse_lowlevel.c#L3549)). `/dev/fd/N` only skips the mount, not the INIT. |
| L2 libfuse `fuse_session_custom_io` + synthetic INIT, after re-exec | Works. The custom `read` returns a copy of the original `fuse_init_in`, and the custom `writev` swallows the reply, which matched the original byte for byte. Same PID; the old handle still reads; 3.2 ms from exec to serving. |
| L3 default libfuse 3.18.3 build | `fuse_session_custom_io` returns -95 (ENOTSUP). 3.18 compiles it out unless built with `-Denable-custom-io=true` ([lib/fuse_lowlevel.c](https://github.com/libfuse/libfuse/blob/fuse-3.18.3/lib/fuse_lowlevel.c#L4306)), so distribution libfuse builds can't do L2. |
| L4 a different implementation adopts the fd (rawfs INIT, then llfs) | libfuse computes its own INIT reply (flags `0x40409029`, `max_write` 1 MiB), while the kernel keeps rawfs's (`0x40440000`, 128 KiB). Basic ops still work, but the successor now believes in parameters that the kernel does not use. |

## Conclusions

1. **Pass the fds; don't run one process per volume.** The kernel keeps the whole connection in the `fuse_conn`: negotiated INIT parameters, nodeids, open files and queued requests. Any process holding the fd can serve it, without a new INIT (F1, F5b, F5c: 0 INITs, open handles keep working). Across 30 handoffs under a stat loop no request failed (F6b). JuiceFS itself relies on this for its "smooth upgrade": mount pods send their FUSE fd to the CSI node plugin, and the new mount pod takes it back ([JuiceFS blog](https://juicefs.com/en/blog/usage-tips/mount-pod-smooth-upgrade), [CSI docs](https://cf.juicefs.com/docs/csi/upgrade-juicefs-client)). One process per volume therefore does not remove the need for fd passing; it buys isolation. Memory is not the argument either way: about 230 kB PSS per libfuse process (F7). The real per-volume cost is a separate session, lease, cache and connection pool per process.
2. **Something must hold every `/dev/fuse` fd at every instant, including every `FUSE_DEV_IOC_CLONE` fd.** When the last reference closes, the kernel aborts the connection (F4a, F4b). A dropped clone kills the requests read on it (F4c). Put the fds in a holder at mount time, not at upgrade time, so that a crash is survivable as well (F5a). The tested holders were a tiny holder process (cold successor serving in 3.8 ms), `execve` in place (1.5 ms), a hot-standby successor over SCM_RIGHTS (0.4 ms), and the systemd user fdstore (about 21 ms; usable without root). In Kubernetes the natural holder is the CSI node plugin over a hostPath unix socket, as JuiceFS does. The holder can drop an fd when it sees `POLLERR`, which happens once the mount is gone (F5a).
3. **Hand the negotiated INIT state over with the fds and keep it fixed for the life of the mount.** The kernel never renegotiates. A successor must use the original `max_write` (`fuse_dev_do_read` rejects smaller read buffers, [dev.c#L1406](https://github.com/torvalds/linux/blob/v6.17/fs/fuse/dev.c#L1406-L1410)) and the original capability flags. A new daemon version cannot turn on writeback cache, a larger `max_write`, passthrough or a request timeout without a remount. L4 shows an implementation that silently computes different parameters. Store `fuse_init_in` and `fuse_init_out` next to the fd (a memfd works in the fdstore, F5c) and refuse to adopt on a mismatch.
4. **Nodeids and file handles must be derivable from durable state.** The kernel holds nodeids and `fh` values that the previous process chose. The approach that worked: nodeid = inode ID, fh = an ID that the successor can resolve, rebuilt lazily on a miss (F1 `RESCAN`). Lookup counts are lost across a crash, so the daemon must tolerate FORGET for nodes it doesn't know and can't rely on counts to free per-inode state.
5. **Graceful upgrade drains; crash recovery resends.** For an upgrade: stop reading, finish what is in flight, then hand off, so nothing needs a resend. After a crash, the successor writes `FUSE_NOTIFY_RESEND` immediately after takeover. Requeued requests carry bit 63, and replies must echo the unique exactly (F3, F3c). Without the resend, a request the dead process had read stays blocked forever (F2). With `FUSE_REQUEST_TIMEOUT` or a host `fs.fuse.max_request_timeout`, the request instead aborts the whole mount after the timeout (F8). Never negotiate a request timeout shorter than the worst-case restart.
6. **Replayed mutating requests need deduplication.** A resent MKDIR that the dead daemon had already applied came back as EEXIST to the application (F3b). Every mutating MetaStore operation from the client daemon needs an idempotency key that survives the crash, for example (mount, unique without bit 63). The unique is stable across a resend but unique only within one connection.
7. **Negotiate `FUSE_PARALLEL_DIROPS`.** Without it, one unanswered LOOKUP blocks every lookup in that directory for the whole handoff (F2b).
8. **Requests during the gap block and then succeed; they don't fail** (F6a: 441 ms gap, then success). On this machine the client-visible stall was 0.7 ms for a hot standby, 1.7 ms for re-exec, 4.2 ms for a cold start from the holder and 21–27 ms through systemd (F6b medians; the noise floor here is 5–9 ms).
9. **The daemon must not unmount on exit or SIGTERM, and must not rely on `auto_unmount`.** fusermount3's watchdog is tied to its socket. It disappears when that socket isn't handed on (F9b) and does nothing for unprivileged mounts without `allow_other` (F9a). Unmounting belongs to the CSI `NodeUnpublish`/`NodeUnstage` path.
10. **libfuse 3.18.3 is a poor fit for the handoff path.** `/dev/fd/N` still waits for INIT and answers EIO (L1). Skipping INIT needs `fuse_session_custom_io` with a synthetic INIT (L2), and that is compiled out of default builds (L3). There is no API to send RESEND. The FUSE layer we pick (C or Rust) must let a session adopt an existing fd with saved INIT state, send raw notifies, and echo the full 64-bit unique.

## Not tested

- Root, `allow_other`, containers, other mount namespaces, a real Kubernetes CSI node plugin as the holder. None of these are possible without root here.
- Transport over `io_uring` (`fuse.enable_uring=N` on this kernel). Whether ring queues survive a handoff is open.
- Passthrough backing IDs (`FUSE_DEV_IOC_BACKING_OPEN` needs `CAP_SYS_ADMIN`).
- `FUSE_NOTIFY_INC_EPOCH`, which a successor could use to invalidate all cached dentries.
- Writeback-cache dirty pages and mmap during the gap, FUSE_INTERRUPT for a request the successor never saw, and a crash with many requests in flight across several worker threads.
- CPU per operation: the cost here is a one-off gap per restart, measured as time.
