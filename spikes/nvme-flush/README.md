# NVMe flush latency spike

**Question.** What is the flush latency of a common consumer NVMe drive, and how does it change with the bytes written per flush? A durable write to the [one log per disk](../../docs/design.md#on-disk-format) costs one write and one flush per group commit, so the answer sets the durable-write latency floor on homelab hardware, the group-commit size, and whether a commit may ever use more than one flush.

**Setup.** Linux 6.17.0-1033-oem, Ubuntu 24.04, Intel Core Ultra 5 235U laptop (14 CPUs). One drive: UMIS RPEYJ512MML1QWQ, 512 GB, firmware 1.0Q06C1, PCIe 4.0 x4. It is the root disk, ext4 `rw,relatime` (`data=ordered`, `commit=5`, barriers on). [flush.c](flush.c) is a C harness. It does `O_DIRECT` `pwrite` then `fdatasync` on a 256 MiB file that was `fallocate`d and then written in full once, so every later write is a pure overwrite and `fdatasync` has no journal work. It times the write and the flush separately. It counts the flushes the device actually received, and their device time, from `/sys/block/nvme0n1/stat` (fields 16 and 17). It subtracts a background rate measured while idle just before each test. fio 3.36 is built from a shallow clone. bpftrace 0.20.2 and nvme-cli 2.8 come from Ubuntu `.deb`s unpacked into `vendor/sysroot`. No root is needed except for [trace-root.sh](trace-root.sh) (eBPF and `nvme id-ctrl`), which has not been run yet.

Other agents were compiling and benchmarking on the same machine and disk throughout. Each test records `loadavg` and the background flush rate. [results.txt](results.txt) is the quietest of three full runs (load 2.9 to 5.1; 1,294 MiB written by all processes, almost all of it this run). [results-run1.txt](results-run1.txt) ran while load rose from 2.2 to 14 (3,817 MiB written by all processes). [results-run2.txt](results-run2.txt) ran at load 12 to 15 (4,863 MiB). N2d was added after the runs: [results-n2d.txt](results-n2d.txt) has it twice.

```
./fetch.sh               # fio built from a tag; bpftrace, nvme-cli from .debs into vendor/sysroot (no root)
./build.sh               # bin/flush
./run.sh [tag]           # every no-root test, about 5 min, writes ~1.3 GB, then deletes work/data -> results[-tag].txt
sudo ./trace-root.sh     # nvme id-ctrl/features + per-command latency from nvme tracepoints -> results-ebpf.txt
```

`write requests/op` in the raw output counts an fdatasync's empty PREFLUSH write as one write request, because blk-mq accounts the containing request and not the flush request ([blk-mq.c#L1046-L1051](https://github.com/torvalds/linux/blob/v6.17/block/blk-mq.c#L1046-L1051)). So 2.00 per op in N2 means one data write. The CPU-per-op figures come from per-op `getrusage(RUSAGE_THREAD)`. They are reliable over thousands of ops, but not for N6b/c, where n = 10 and the time between ops is long.

## Conclusions

1. **The durable-write floor on this drive is about 1 ms per group commit: p50 0.95 ms, p99 2.4 ms, about 1,050 to 1,090 commits/s per stream** (N2, N8a). The flush alone is only 215 µs p50. The rest is device time charged to the write that follows a flush (12.8 µs on its own, 332 µs after a flush). So "flush latency" must always be measured as write + flush. The block-volume latency budget on consumer drives starts at ~1 ms per replica, before the network, and the replicas' flushes overlap. A DRAM-less drive without PLP gives no µs-class durability; only PLP datacenter drives do.
2. **Group commit has a flat cost up to 64 KiB and gives bandwidth above that.** Commits of 4 to 64 KiB cost the same 0.95 to 0.98 ms. 256 KiB costs 1.9 ms, 1 MiB 2.3 ms (460 MB/s durable), 4 MiB 4.3 ms (948 MB/s) (N3). Keep the design's rule, "all writes that arrived during the last flush", and cap a record with a setting, `max_group_commit_bytes`, default 1 MiB: past 1 MiB, latency grows faster than throughput. Write each record with one contiguous write (16 separate 4K writes cost 15 to 72% more, N3b) or one batched io_uring submission.
3. **Exactly one flush per group commit, and never a second flush to order a header after its data.** Each extra flush costs a full ~1 ms (data + flush + header + flush = 1.93×, N3b). The record header must make a torn record detectable on its own, using the per-block CRC32C that the one-log-per-disk design already requires plus a checksum over the header. Then the header and data can go in the same write and the same flush.
4. **Use write + flush, never O_DSYNC/RWF_DSYNC, FUA or fsync, for ChunkStore data.** On this drive a FUA write takes 2.2 ms against 0.95 ms for write + fdatasync (N5). Linux switches to FUA by itself for dsync direct overwrites on any drive that advertises it. fsync adds a journal commit whose commit block is itself PREFLUSH|FUA: 2.5 ms (N5c, N8b). The io_uring driver should use `IORING_OP_FSYNC` with `IORING_FSYNC_DATASYNC`; an SPDK driver sends NVMe Flush. Drives with PLP may be faster with FUA, so make this a driver setting (`durability = flush | fua`) with `flush` as the default.
5. **Segments kept in files must be written once before they are used; a raw block device avoids the question.** A write into `fallocate`d but never-written extents makes fdatasync commit the ext4 journal: 2.5 ms instead of 0.95 ms (N2d). The ChunkStore either zero-fills segments when it creates them (a one-time cost per segment, at about 1.3 GB/s here: 256 MiB in 203 ms, N2 prepare) or reuses old segments after cleaning. Any file the daemon grows and then syncs, such as its state directory, pays the same journal commit.
6. **An idle disk adds about 1 ms to the next commit.** After ≥ 10 ms idle the commit p50 rises: 1.2 ms after 10 ms, 1.9 to 2.1 ms after 100 ms to 3 s, with a 15.8 ms outlier after 3 s (N6). Spinning the CPU does not help, so this is the drive or link power state. A lightly loaded homelab cluster sees ~2 ms local commits, not 1 ms. Benchmarks and latency SLOs must include idle gaps. Disabling APST (`nvme_core.default_ps_max_latency_us=0`) is a documented knob for latency-sensitive installs, untested here.
7. **One commit loop and one flush per disk, as in the design's [on-disk format](../../docs/design.md#on-disk-format); never per volume, PG or Raft shard.** The kernel does not merge flushes across CPUs (N7). The drive overlaps two write + flush streams at unchanged latency (2,065/s, p50 984 µs). Four or more add latency (p50 1.2 to 2.4 ms, p99 ~5 ms) without reliable gains, and 8 fall to ~1,700 to 2,000/s at p50 3.6 to 4.3 ms. So the one shared flush is the right shape. A second flusher on the same drive (the OS, or the daemon's state directory) costs the log nothing at this drive's two-stream depth, but per-volume or per-shard flushing would. That holds whether or not the flushes would merge on one CPU (N7b).

Not covered: other drives (DRAM consumer drives, QLC drives, PLP datacenter drives, SATA SSDs). Raw block devices without ext4. io_uring instead of psync. Power-cut tests, which would show whether this drive honours flush at all. The device-side split from eBPF, which needs `sudo ./trace-root.sh`.
