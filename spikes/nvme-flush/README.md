# NVMe flush latency spike

**Question.** What is the flush latency of a common consumer NVMe drive, and how does it change with the bytes written per flush? A durable write to the [one log per disk](../../docs/design.md#on-disk-format) costs one write and one flush per group commit, so the answer sets the durable-write latency floor on homelab hardware, the group-commit size, and whether a commit may ever use more than one flush.

**Setup.** Linux 6.17.0-1033-oem, Ubuntu 24.04, Intel Core Ultra 5 235U laptop (14 CPUs). One drive: UMIS RPEYJ512MML1QWQ, 512 GB, firmware 1.0Q06C1, PCIe 4.0 x4. It is the root disk, ext4 `rw,relatime` (`data=ordered`, `commit=5`, barriers on). [flush.c](flush.c) is a C harness. It does `O_DIRECT` `pwrite` then `fdatasync` on a 256 MiB file that was `fallocate`d and then written in full once, so every later write is a pure overwrite and `fdatasync` has no journal work. It times the write and the flush separately. It counts the flushes the device actually received, and their device time, from `/sys/block/nvme0n1/stat` (fields 16 and 17). It subtracts a background rate measured while idle just before each test. fio 3.36 is built from a shallow clone. bpftrace 0.20.2 and nvme-cli 2.8 come from Ubuntu `.deb`s unpacked into `vendor/sysroot`. Only [trace-root.sh](trace-root.sh) needs root. It reads the drive's identify data, features and SMART log with nvme-cli (E0), then reruns N2 to N8a (E1 to E9) under [nvme-lat.bt](nvme-lat.bt), which times every NVMe command from the driver's `nvme_setup_cmd` tracepoint to `nvme_complete_rq`: the time the command spends in the device, against the time the harness sees. It ran once on a quiet machine (load 0.4 to 1.7): [results-ebpf.txt](results-ebpf.txt). [results-fua-rerun.txt](results-fua-rerun.txt) reruns N5 three times without tracing, to check E4.

Other agents were compiling and benchmarking on the same machine and disk throughout. Each test records `loadavg` and the background flush rate. [results.txt](results.txt) is the quietest of three full runs (load 2.9 to 5.1; 1,294 MiB written by all processes, almost all of it this run). [results-run1.txt](results-run1.txt) ran while load rose from 2.2 to 14 (3,817 MiB written by all processes). [results-run2.txt](results-run2.txt) ran at load 12 to 15 (4,863 MiB). N2d was added after the runs: [results-n2d.txt](results-n2d.txt) has it twice.

```
./fetch.sh               # fio built from a tag; bpftrace, nvme-cli from .debs into vendor/sysroot (no root)
./build.sh               # bin/flush
./run.sh [tag]           # every no-root test, about 5 min, writes ~1.3 GB, then deletes work/data -> results[-tag].txt
sudo ./trace-root.sh     # nvme id-ctrl/features + per-command latency from nvme tracepoints -> results-ebpf.txt
# results-fua-rerun.txt: bin/flush prep work/data-fua, then 3 x bin/flush qd1 with mode=empty n=3000,
# mode=dsync n=1000 (random, then seq=1), mode=fdatasync n=1000; all with bg_secs=1
```

`write requests/op` in the raw output counts an fdatasync's empty PREFLUSH write as one write request, because blk-mq accounts the containing request and not the flush request ([blk-mq.c#L1046-L1051](https://github.com/torvalds/linux/blob/v6.17/block/blk-mq.c#L1046-L1051)). So 2.00 per op in N2 means one data write. The CPU-per-op figures come from per-op `getrusage(RUSAGE_THREAD)`. They are reliable over thousands of ops, but not for N6b/c, where n = 10 and the time between ops is long.

In [results-ebpf.txt](results-ebpf.txt), every flush shows up under first key 0 (other processes), because blk-mq sends a flush from the kblockd workqueue, not from the thread that called fdatasync ([blk-flush.c#L330-L334](https://github.com/torvalds/linux/blob/v6.17/block/blk-flush.c#L330-L334), [blk-mq.c#L1577-L1580](https://github.com/torvalds/linux/blob/v6.17/block/blk-mq.c#L1577-L1580)); the flush counts match the harness's ops plus the background rate. Ignore `@inflight_at_flush_submit`: the counter is a global map updated from every CPU without atomics, so it drifts (E8 even records values below 1). Device time per thread-second (E7, E8) adds the device time of all the harness's writes and flushes, over threads × 3 s per phase.

## Conclusions

1. **The durable-write floor on this drive is about 1 ms per group commit, and 98% of it is in the device: p50 0.95 ms, p99 2.4 ms, about 1,050 to 1,110 commits/s per stream** (N2, N8a, E1, E9). The device spends about 0.9 ms on each write + flush (E1: 418 µs write + 478 µs flush, means); the kernel and host add 20 µs. The device splits that time two ways: either a ~1.1 ms flush and a ~10 µs next write, or a ~0.2 ms flush and a 0.3 to 1 ms next write. A flush p50 (215 µs) on its own therefore means nothing; measure write + flush. No driver lowers this floor: io_uring or SPDK can remove at most the 20 µs the kernel and host add. The block-volume latency budget on consumer drives starts at ~1 ms per replica, before the network, and the replicas' flushes overlap. A DRAM-less drive without PLP gives no µs-class durability; only PLP datacenter drives do.
2. **Group commit has a flat cost up to 64 KiB and gives bandwidth above that.** Commits of 4 to 64 KiB cost the same 0.93 to 0.98 ms. 256 KiB costs 1.2 to 1.9 ms depending on the run, 1 MiB 2.3 to 2.4 ms (460 MB/s durable), 4 MiB 4.3 to 4.5 ms (950 MB/s) (N3, E6). Keep the design's rule, "all writes that arrived during the last flush", and cap a record with a setting, `max_group_commit_bytes`, default 1 MiB: past 1 MiB, latency grows faster than throughput. Write each record with one contiguous write (16 separate 4K writes cost 15 to 72% more, N3b) or one batched io_uring submission.
3. **Exactly one flush per group commit, and never a second flush to order a header after its data.** Each extra flush costs a full ~1 ms (data + flush + header + flush = 1.93×, N3b). The record header must make a torn record detectable on its own, using the per-block CRC32C that the one-log-per-disk design already requires plus a checksum over the header. Then the header and data can go in the same write and the same flush. The drive promises atomicity on power failure for one 512 B logical block only (`awupf` = 0, E0), so even a single 4 KiB block can tear, and the per-block checksum is what catches it.
4. **Use write + flush, never O_DSYNC/RWF_DSYNC, FUA or fsync, for ChunkStore data.** On this drive a 4K FUA write takes 2.2 to 2.3 ms in the device, against about 0.9 ms for write + flush (N5, E4, E1). The cost is the drive's, not the kernel's, and a FUA write straight after a flush is no faster (E5). Linux switches to FUA by itself for dsync direct overwrites on any drive that advertises it. fsync adds a journal commit whose commit block is itself PREFLUSH|FUA: 2.5 ms (N5c, N8b, E5). The io_uring driver should use `IORING_OP_FSYNC` with `IORING_FSYNC_DATASYNC`; an SPDK driver sends NVMe Flush. Drives with PLP may be faster with FUA, so make this a driver setting (`durability = flush | fua`) with `flush` as the default.
5. **Segments kept in files must be written once before they are used; a raw block device avoids the question.** A write into `fallocate`d but never-written extents makes fdatasync commit the ext4 journal: 2.5 ms instead of 0.95 ms (N2d). The ChunkStore either zero-fills segments when it creates them (a one-time cost per segment, at about 1.3 GB/s here: 256 MiB in 203 ms, N2 prepare) or reuses old segments after cleaning. Any file the daemon grows and then syncs, such as its state directory, pays the same journal commit.
6. **An idle disk adds about 1 ms to the next commit.** After ≥ 10 ms idle the commit p50 rises: 1.2 ms after 10 ms, 1.9 to 2.1 ms after 100 ms to 3 s, with a 15.8 ms outlier after 3 s (N6). Spinning the CPU does not help, so this is the drive or link power state. APST puts this drive in PS3 (2 ms exit latency) after 100 ms idle and PS4 (21 ms) after 2 s (E0), which fits the step at 100 ms and the outlier; the step at 10 ms is not APST. A lightly loaded homelab cluster sees ~2 ms local commits, not 1 ms. Benchmarks and latency SLOs must include idle gaps. Disabling APST (`nvme_core.default_ps_max_latency_us=0`) is a documented knob for latency-sensitive installs, untested here.
7. **One commit loop and one flush per disk, as in the design's [on-disk format](../../docs/design.md#on-disk-format); never per volume, PG or Raft shard.** Neither the kernel nor the drive folds flushes for us. The kernel folds only flushes queued on one hardware queue, and a folded fdatasync then waits in the kernel for the flush in flight (N7b, E7). With one queue per CPU, threads on different CPUs never share one (N7). The drive overlaps two write + flush streams at unchanged latency (2,065 to 2,097/s, p50 984 to 988 µs). With more, commands queue in the device and each flush still costs its own device time: the drive completes at most about 2,800 flushes a second (E8: 2,097, 2,772 and 1,960/s at 2, 4 and 8 threads). Four streams add latency (p50 1.2 to 2.4 ms, p99 ~5 ms) without reliable gains, and 8 fall to ~1,700 to 2,000/s at p50 3.6 to 4.3 ms. So the log must fold commits itself, one flush per round covering every write queued during the last flush. A second flusher on the same drive (the OS, or the daemon's state directory) costs the log nothing at this drive's two-stream depth, but per-volume or per-shard flushing would.

Not covered: other drives (DRAM consumer drives, QLC drives, PLP datacenter drives, SATA SSDs). Raw block devices without ext4. io_uring instead of psync. Power-cut tests, which would show whether this drive honours flush at all. Pairing each flush with the write after it, which would confirm the two-way split in conclusion 1 (needs a per-command trace keyed by the harness's op). The device side of the idle-gap tests (N6), which trace-root.sh does not run. The cause of E4's 8 to 16 ms FUA writes.
