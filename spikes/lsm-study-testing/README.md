# LSM study: testing

**Question.** How do Pebble and RocksDB test that their LSM trees, logs and recovery are correct, and which of those practices should rock-solid's simulator and test suites adopt, given a sans-IO core under deterministic simulation, one log per raw disk with no filesystem, sorted runs held in memory, and several indexes per log? In particular: should `internal/lsm` and the chunk index get a metamorphic test (Pebble's same-ops-under-different-options check), does our crash oracle match RocksDB's expected state with trace replay, does the simulated disk drop unsynced writes as strictly as Pebble's crashable `MemFS` and RocksDB's `FaultInjectionTestFS`, and which of their historical bug classes become scenarios?

**Setup.** Linux 6.18.44 in a Firecracker VM, 4 vCPUs shared with six other agents, Go 1.27.0, rock-solid at `5a5f5e2` (`internal/lsm` unchanged since `86c47be`: Cassandra's bucket picker, which [design.md](../../docs/design.md#on-disk-format) now replaces with RocksDB's universal rules, and no Bloom filters yet). Sources read, not built: Pebble master at [`a7b8321871e3`](https://github.com/cockroachdb/pebble/tree/a7b8321871e3e3c19be21eaf42a6aaa7e2d04f23) (2026-10-14) and v2.1.7, RocksDB [v11.8.1](https://github.com/facebook/rocksdb/tree/v11.8.1); `fetch.sh` makes the same shallow clones. Links below are `file:line` at those refs (Pebble `P:` = `github.com/cockroachdb/pebble/blob/a7b8321871e3/`, RocksDB `R:` = `github.com/facebook/rocksdb/blob/v11.8.1/`).

The prototype is a metamorphic harness over the real `internal/lsm`, built through the module's `replace` directive:

- [meta/meta.go](meta/meta.go): a seeded op generator in the style of Pebble's (`P:metamorphic/generator.go:184`): puts, removals, gets, floors, scans, point-in-time views (open, read, close), flushes, failed flushes (`flushfail n`: a checkpoint that fails after n pieces), compactions and restarts, drawn from a weighted deck; keys from six letters, a quarter of a put's keys new and the rest reused, so ops collide (Pebble's sets take a new key half the time, `P:metamorphic/generator.go:1542`). Ops have a text form (`put aa v26x`, `flush`, `floor aca`), so a failure is an ops file. An executor runs ops under an option set and records one history line per op; a reducer drops chunks of ops while the failure persists, as Pebble's `--try-to-reduce` does (`P:internal/metamorphic/reduce_test.go:36`). A map model is the reference.
- [engine/engine.go](engine/engine.go): the tree over a fake log that keeps every live piece and drops the pieces `CheckpointDone` and `FlushFailed` report dead. A restart throws the tree away and recovers like the real node: load the newest manifest's runs with `LoadRun`, then replay the writes after the manifest's replay point (the freeze of the memtable it wrote, or of an earlier frozen one a failed flush left).
- Seven option sets, chosen like Pebble's standard options, which push one knob each to an extreme (`P:metamorphic/options.go:468`: `l0_compaction_threshold=1`, `block_size=1`, `mem_table_size=2000`...):

| Set | Piece | Flushes | Compaction | Other |
| --- | --- | --- | --- | --- |
| F | 1 MiB | none: memtable only, a restart replays every write | none | |
| A | 1 MiB | the generated ones | the generated ones, installed at once | |
| B | 4 KiB | generated, and after every 40 writes | after every flush until none is due | |
| C | 256 B | generated, and after every 10 writes | never (up to 300 runs) | |
| D | 512 B | generated, and after every 25 writes | picked at a `compact` op, run and installed between the pieces of the next flush | up to 4 following writes run between a flush's pieces |
| E | 1 KiB | every flush first fails after 1 piece, then runs; after every 30 writes | eager | a restart after every flush |
| G | 4 KiB | after every 2 writes | after every 40th flush only, so a merge sees 40 runs, more than the 32 a bucket takes, and leaves older runs out | |

- Planted bugs ([plant.sh](plant.sh)) in copies of `internal/lsm`, each one line: **P1** a flush drops every removal, even one hiding a key in an older run; **P2** a compaction's output is installed as the oldest run; **P3** a restore loads runs in the order the manifest lists them, not by age; **P4** reads skip the frozen memtable; **P5** a compaction drops removals that hide keys in runs older than its inputs.
- [dd/](dd/): the reduced failures as `github.com/cockroachdb/datadriven` regression cases ([dd/testdata/regressions](dd/testdata/regressions)), the format Pebble (142 test files) and etcd-raft use.
- `-crc`: the CPU of CRC32C over a compaction's input pieces against the compaction itself.

```
./fetch.sh   # optional: the Pebble and RocksDB sources cited
./run.sh     # about 15 minutes on the shared VM; writes results.txt
```

Expected before the run: **T1** the real tree reads the same as the model under every set; **T2** every plant fails at least one set, P3 only sets with restarts, P4 only sets that read while a memtable is frozen (failed flushes, writes between pieces); **T3** `internal/lsm`'s own unit tests catch each plant; **T4** the reducer brings a failure to under 10 ops; **T5** the regression file passes on the real tree; **T6** CRC32C costs under 10% of a compaction.

## Results

Raw output: [results.txt](results.txt).

### Prototype

| Test | Result |
| --- | --- |
| T1 `internal/lsm`, 200 seeds × 3,000 ops × 7 sets | **0 of 200 seeds differ** from the model or between sets. Seed 0 alone: 177 to 937 flushes per set, up to 199 failed ones (E), up to 68 compactions, 139 restarts (E), up to 295 runs (C); 16,687 writes ran between a flush's pieces over all seeds. A 3,000-op run costs about 99 ms per option set (1,600 runs in 2 min 38 s) on the shared VM |
| T2 planted bugs, 20 seeds each | Every plant fails: **P1** 20 of 20 seeds, every set with flushes; **P2** 20 of 20, **only under G**; **P3** 20 of 20, every set with flushes (all have restarts); **P4** 18 of 20 (A 8, B 8, D 17, E 12; C and G 0, since their flush every 2 or 10 writes writes a frozen memtable out before a read reaches a key only it holds); **P5** 20 of 20, **only under G**. A first run without G missed P5 in all 10 seeds: with at most 32 runs a bucket always reaches the oldest run, so a merge has no older run to hide keys in. Every divergence from the model was also a divergence from set F, so the history diff alone found each one |
| T3 `internal/lsm`'s unit tests against the plants | Every plant fails at least one: P1 four tests, P2 one (`TestCompactionKeepsRemovalsAboveOlderRuns`), P3 one (`TestRestoreIsRunsPlusReplay`), P4 three, P5 one. The hand-written scenarios already hold these five; the metamorphic test finds them without knowing where to look |
| T4 reduction | P1 from 3,000 ops to **5** (`put aa`, `flush`, `del aa`, `flush`, `floor aca`), P3 to **7**; P2 and P5 to 76 and P4 to 354, because their failure needs a cadence set by the option (40 flushes before a merge, a failed flush 25 writes from the next), which removing ops cannot shorten |
| T5 datadriven regressions | The reduced P1 and P3 cases pass on `internal/lsm` as [dd/testdata/regressions](dd/testdata/regressions); `go test -rewrite` writes their expected output |
| T6 CRC32C over compaction inputs | CRC32C costs **3.8 to 5.1%** of the merge it guards: 605 µs against 12.6 ms for four 1 MiB runs, 2.5 ms against 48.8 ms for four 4 MiB runs, 46 µs against 1.2 ms for four 96 KiB runs of 4 KiB pieces |

| Practice | Pebble | RocksDB | For us |
| --- | --- | --- | --- |
| Same ops under several configurations, histories compared | The metamorphic test: one ops file per seed, ~30 standard option sets at extremes plus as many random ones, each run in its own process, histories diffed line by line against the first (`P:metamorphic/meta.go:158`, `:311`; `P:metamorphic/options.go:468`). `replace_single_delete=true` runs the same ops with each SingleDelete replaced by a Delete (`options.go:559`, `ops.go:383`) | No cross-configuration diff; `db_crashtest.py` randomizes options per run and checks each run against the expected state (`R:tools/db_crashtest.py:380`) | **ADOPT** (T1, T2): P2 and P5 show only under G, an option set at an extreme |

## Conclusions

1. **Each internal choice needs an option set at its extreme.** P2 and P5 showed only under G, where 40 runs wait before a merge, more than a bucket's 32; no ordinary cadence produced a merge with older runs left out. Pebble's standard options set thresholds to 1 for the same reason.
2. **The history diff finds what the model finds.** Every divergence from the map model was also a divergence between option sets, so new ops (views, range removals, frozen maps) are checked by comparison before anyone writes their model. The model stays, because a bug every set shares, such as one in the memtable, shows in no diff.
3. **Reduction works when the structural steps are ops.** A failure caused by explicit flushes, failed flushes and restarts reduced from 3,000 ops to 5 and 7; one that needs a cadence set by an option stayed at 76 to 354. A reduced case becomes a regression file only after its cadence is rewritten as explicit ops.
4. **The targeted unit tests still matter.** `internal/lsm`'s own tests caught all five plants, P2 and P5 with one test each; the metamorphic test is the net for what nobody wrote a scenario for, at about 99 ms per set per 3,000-op seed.
5. **CRC32C over a compaction's inputs costs 3.8 to 5.1% of the merge,** on the worker goroutine that runs it, so a merge can verify a checksum per run block before it copies a block that memory corruption changed into a new run with a fresh, valid checksum, as RocksDB's compaction reads with `verify_checksums`.
6. **Our crash model is the strictest of the three;** the simulated disk's gaps are injected write, flush and damaged-read errors and a test that crashes or fails at every action index, which both engines have.
7. **The option sets grow with the tree.** With the universal picker and per-run Bloom filters that [design.md](../../docs/design.md#on-disk-format) now specifies, the sets add filters off and a filter that answers every probe "maybe" (Pebble's `filter_policy=none`), two merges of disjoint adjacent runs at once (Pebble's `max_concurrent_compactions=2`), a fixed run limit of four against the auto-tuned one, and range removals against the point removals of the keys they cover (Pebble's `replace_single_delete`). None may change a read.
