# FUSE descriptor handoff spike (root)

**Question.** Does handing the `/dev/fuse` descriptor to a successor survive a daemon crash in the places the [FUSE restart spike](../fuse-restart/) could not go without root: a separate holder process standing in for the CSI node plugin, `allow_other` with an application of another uid, a mount made in one mount namespace and used from another, and the FUSE-over-io_uring transport? And can go-fuse adopt an initialized descriptor with saved `INIT` parameters, send `FUSE_NOTIFY_RESEND`, echo full 64-bit request IDs and serve from our event loops, or does the frontend speak `/dev/fuse` itself? This answers two open questions in [docs/design.md](../../docs/design.md) ("Roadmap and open questions").

## Setup

- Linux 6.18.44 (Firecracker guest `6.18.44-fc-v139`), x86_64, 4 vCPUs (4 possible CPUs, so 4 io_uring queues), root, `CONFIG_FUSE_IO_URING=y` with `fuse.enable_uring` set to `Y`. Kernel FUSE protocol 7.45. Kernel sources cited at the stable tag [v6.18.44](https://github.com/gregkh/linux/tree/v6.18.44/fs/fuse) that the guest runs, which differs from `v6.18` in `dev_uring.c` (cancel and crash paths were backported), and at mainline `master` [32c52ec8](https://github.com/torvalds/linux/tree/32c52ec87d6245ee2d12ed5dd509e40062939b50/fs/fuse) (7.3-rc7) where they still apply. go-fuse [v2.12.0](https://github.com/hanwen/go-fuse/tree/v2.12.0) with Go 1.27.0. util-linux 2.39.3 (`unshare`, `nsenter`, `setpriv`). Written against rock-solid commit `676095bf`; nothing here imports the module.
- `hofs.c` is `../fuse-restart/rawfs.c` reworked for root: it mounts with `mount(2)` (`fd=N,rootmode=40000,user_id=0,group_id=0[,allow_other]`), puts its descriptor into the holder (`hofs hold`, a separate long-lived process) right after `INIT`, and a successor (`hofs get`) takes it back. `--batch 16 --delay-us 2000` reads up to 16 requests before answering any, as an event loop does, so a kill lands with several requests read and unanswered. `--uring` negotiates `FUSE_OVER_IO_URING` and serves all 4 queues (2 entries each) from one thread with raw `io_uring_setup`/`io_uring_enter` and 128-byte SQEs. `--shm` puts the ring buffers, a per-entry state word and a staged copy of each reply in a memfd mapped at a fixed address and handed to the holder with the descriptor, so a successor maps the same memory at the same address.
- `worker.py` runs 4 processes that each write a 4 KiB block stamped with (worker, sequence) to their own file through the mount (`FOPEN_DIRECT_IO`, so every write and read reaches the daemon), read it back and compare. `run.py` drives the scenarios, prints each expected outcome before it runs, and cleans up with fusectl aborts and lazy unmounts. `gofuse/` is a Go program against go-fuse v2.12.0.
- **Stand-ins and limits.** No Kubernetes: the CSI node plugin is a holder process in its own mount namespace, the kubelet directory is a self-bind-mount made `shared`, a daemon container with `mountPropagation: Bidirectional` is `unshare -m --propagation unchanged`, and an application container with `HostToContainer` is a namespace whose copy of the kubelet directory is `rslave`. A real CSI pod adds a different PID namespace and cgroup (irrelevant to `SCM_RIGHTS`), a hostPath directory for the holder's socket, kubelet's own bind mounts, and possibly SELinux labels and pod user namespaces, none tested here. The machine was shared with six other agents running benchmarks on the same 4 cores (load average about 6), so the timings are upper bounds; this spike counts outcomes, not CPU.

```sh
cd spikes/fuse-handoff
./fetch.sh                    # Linux 6.18.44 fs/fuse + uapi headers, mainline dev*.c, go-fuse v2.12.0 (for reading)
./build.sh                    # bin/hofs
(cd gofuse && go build -o ../bin/gofuse .)
echo Y > /sys/module/fuse/parameters/enable_uring
U3_RUNS=20 python3 run.py > results.txt   # as root, ~4 min; or: python3 run.py H1 U1 G1
```

## Results

Raw output: [results.txt](results.txt). 126 checks passed and 4 failed in the recorded run; the 4 failures are findings, explained in U3 and G1.

| Test | Result |
| --- | --- |
| H1 holder process, daemon SIGKILLed with I/O in flight, cold successor resends (5 runs) | **No application error in any run.** At each kill 5 requests were waiting (4 workers and a hung `LOOKUP`); the successor received 1 to 4 of the I/O requests and the `LOOKUP` again with bit 63 set, answered them, and every block read back as written. No `INIT`. The successor was serving 3 to 10 ms after the kill; the worst I/O operation took 32 to 41 ms on this loaded machine. |
| H2 `allow_other`, I/O as uid 65534 across the same crash | Without `allow_other`, uid 65534's `stat` fails with `EACCES` ([`fuse_allow_current_process`](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dir.c#L1491-L1504)). With it, 4 workers as uid 65534 ran across the kill and handoff with 0 errors. `allow_other` belongs to the connection, so the successor needs nothing to keep it. |
| H3 daemon, holder, application and successor in four mount namespaces | The mount made in the daemon's namespace (kubelet directory shared with the host) propagated to the host and into the application's `rslave` namespace, and the plugin's bind mount to the pod path did too. **SIGKILL left the daemon's namespace with no process, and the mount stayed in the host and the application's namespace.** The successor ran in a private namespace where the kubelet tree was unmounted, so it could not see the mount at all, and served it from the descriptor alone: 0 application errors. Control: a mount made in a namespace with private propagation stayed invisible to the host. Unmounting on the host removed it from the application's namespace. |
| U0 io_uring transport | 20,525 write-and-verify operations, 0 errors; every request after `INIT` came through the ring, none through `read(/dev/fuse)`. |
| U1 io_uring daemon SIGKILLed idle, a request made in the gap | (a) A successor reading `/dev/fuse` never sees it: once the ring is ready, `fiq->ops` sends every request to a ring queue ([dev_uring.c#L1032](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dev_uring.c#L1032)) and nothing switches it back, so **a ring connection cannot fall back to read and write.** (b) After the successor registers fresh entries on every queue the gap request is **still blocked**: `REGISTER` only makes an entry available ([`fuse_uring_do_register`](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dev_uring.c#L1001-L1037)), and a request queued while its queue had no entry ([#L1331](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dev_uring.c#L1331)) is dispatched only after a later commit on the same queue. (c) One new request from the same CPU (queues are per CPU, [#L1282](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dev_uring.c#L1282)) is served, and its commit releases the gap request, 2.3 s late. Unmount afterwards: 15 ms. |
| U2 io_uring daemon SIGKILLed with a request it had fetched | **The request stays blocked for good**, through re-registration, `FUSE_NOTIFY_RESEND` and a request from every CPU: `fuse_resend` requeues only the processing lists of `/dev/fuse` devices ([dev.c#L2011-L2031](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dev.c#L2011-L2031)), and a fetched ring request sits on its queue's own list ([dev_uring.c#L1236](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dev_uring.c#L1236)). The same is true at mainline master (`fuse_chan_resend`). Only aborting the connection ended it (`ECONNABORTED`). |
| U3 ring buffers in a memfd the holder keeps; the successor maps it at the same address, answers what the dead daemon had fetched, registers the rest and makes one request per CPU (20 runs) | The fetched `LOOKUP`, 0 to 2 other fetched I/O requests, 0 to 3 requests whose completions died in the old ring, and the gap requests on all 4 CPUs were answered in every run: the kernel keeps the user address each entry registered ([#L1104](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dev_uring.c#L1104)) and copies the reply from it in whichever process commits ([#L840](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dev_uring.c#L840)). **But in 2 of 20 runs (3 operations), and 6 of 87 runs counting development runs, an application write failed with `ECANCELED`.** A request handed to an idle entry of the dying daemon is copied out by task work that runs only once the task is exiting, and then the kernel ends the request with `-ECANCELED` instead of requeueing it ([`fuse_uring_send_in_task`](https://github.com/gregkh/linux/blob/v6.18.44/fs/fuse/dev_uring.c#L1247-L1275); unchanged at master). The failing operations started between 17 ms before and 3 ms after the kill. No successor can prevent this. |
| G1 go-fuse `NewServer` on the initialized descriptor through the `/dev/fd/N` mountpoint | `NewServer` blocks in `handleInit` ([server.go#L272](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/server.go#L272), [#L409-L431](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/server.go#L409-L431)) until a request arrives, handles that `GETATTR` in `INIT`'s place, and **returns no error with kernel settings 0.0** and no negotiated flags. My expectation that this fails was wrong: it silently runs with settings it never received, so every check gated on them (`renameInSize`, `SupportsNotify(NOTIFY_PRUNE)`) answers as for a kernel older than 7.12. A first attempt failed with `EAGAIN` instead, because the predecessor had set `O_NONBLOCK` on the shared open file description, which the successor inherits. |
| G2 go-fuse `ProtocolServer` (transport-free, marked experimental) | A synthetic `INIT` replayed through `HandleRequest` sets its settings, and a resent unique (`0x800000000000014a`) is echoed whole ([request.go#L375](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/request.go#L375)). Each `GETATTR` allocates 2 objects, 1,008 bytes (the `requestAlloc` and its cancel channel, [protocol-server.go#L312-L317](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/protocol-server.go#L312-L317)), about 1.3 µs. |

Source review of go-fuse v2.12.0 (no test needed):

- **Resend:** `NOTIFY_RESEND` is only a name in a debug table ([misc.go#L26](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/misc.go#L26)); the notifications it can send are `INVAL_INODE`, `INVAL_ENTRY`, `STORE_CACHE`, `RETRIEVE_CACHE`, `DELETE` and `PRUNE` ([server.go#L573-L589](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/server.go#L573-L589)), each allocating its request.
- **Saved `INIT`:** the kernel settings and negotiated flags are unexported fields filled only by `doInit` ([protocol-server.go#L14-L45](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/protocol-server.go#L14-L45), [opcode.go#L89-L158](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/opcode.go#L89-L158)); `MountOptions` has no field for them.
- **Request IDs:** `InHeader.Unique` is a `uint64` ([types.go#L688](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/types.go#L688)) copied into the reply, so 64-bit echo already works.
- **Threading:** `Server.loop` starts a goroutine per request (`go ms.handleRequest(req)`, [server.go#L488](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/server.go#L488)) and new reader goroutines on demand ([fusefd.go#L157](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/fusefd.go#L157)). The `RawFileSystem` API is synchronous: the reply is the return value of `Lookup`, `GetAttr`, `Read` ([api.go#L430](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/api.go#L430), [#L441](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/api.go#L441), [#L478](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/api.go#L478)), so a request answered after a ChunkStore round trip needs a goroutine parked on it. Requests are decoded by `unsafe` casts ([request.go#L275-L285](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/request.go#L275-L285)) and tracked under a mutex.
- **io_uring:** no transport; only the capability bit ([types.go#L325](https://github.com/hanwen/go-fuse/blob/v2.12.0/fuse/types.go#L325)).

## Conclusions

1. **The handoff needs only the descriptor, wherever the processes live.** Holder, daemon, successor and application in four mount namespaces, the mounting namespace destroyed by the crash, an application of another uid through `allow_other`: 0 application errors and every in-flight request resent (H1 to H3). The mount and its options belong to the connection, not to the process or namespace that made it.
2. **The daemon's container needs `mountPropagation: Bidirectional`** on the kubelet directory to make the mount visible to the kubelet and pods (H3 control); `Bidirectional` requires a privileged container. The successor needs no mount access, only the descriptor and its saved state.
3. **The holder's socket goes on a hostPath directory both pods mount**; a path-bound Unix socket works across mount namespaces (H3). The holder must check who connects (`SO_PEERCRED`, a root-only directory), since the descriptor is the whole filesystem.
4. **Do not negotiate FUSE over io_uring.** After a daemon crash on Linux 6.18.44 and mainline, requests the daemon had fetched are not resent (U2), requests made during the gap wait for an unrelated request on the same CPU (U1), the connection cannot fall back to `/dev/fuse` (U1), and a request handed to the dying daemon fails with `ECANCELED` (U3). Keeping the ring buffers in shared memory at a fixed address recovers the first two, not the last. The ring becomes worth measuring once the kernel requeues those requests instead.
5. **A successor must set the file flags it needs.** `O_NONBLOCK` lives on the open file description that the holder, the dead daemon and the successor share (G1).
6. **Speak `/dev/fuse` ourselves.** go-fuse cannot be told the saved `INIT` (G1 runs on with zero settings), cannot send `FUSE_NOTIFY_RESEND`, needs a goroutine per in-flight request because its filesystem API returns the reply, and allocates per request even in its transport-free `ProtocolServer` (G2). Its unique echo is the only one of the four requirements it meets. The protocol is a fixed binary layout (the request handling in `hofs.c`, about 15 opcodes for both transports, is about 200 lines of C), which the runtime rules already want as a hand-written, fuzzed codec.
