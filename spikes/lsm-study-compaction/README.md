# LSM compaction study

**Question.** Which compaction policy should the LSM tree of `internal/lsm` follow so that its run count, the bytes it rewrites and the space its runs take stay bounded whatever sizes checkpoint flushes have, and do entries need sequence numbers for it? The [cleaner streams spike](../cleaner-streams/) ran an 80% full disk out of space with 13,025 chunk-index runs, because flushes alternated between small and large and the design's buckets over runs adjacent in age never merged ([open question](../../docs/design.md#roadmap-and-open-questions) "Compaction when flush sizes alternate"). This study reads how Pebble's leveled compaction and RocksDB's leveled, universal and FIFO compaction shape their trees, then replays flush-size sequences through our bucket rule, a port of RocksDB's universal picker and Pebble itself.

**Setup.** Linux 6.18.44 in a Firecracker VM, 4 vCPUs of an Intel Xeon at 2.8 GHz shared with six other agents, Go 1.27.0; everything reported is a count (runs, bytes), not a time. Sources read: Pebble master at [`a7b8321871e3`](https://github.com/cockroachdb/pebble/tree/a7b8321871e3e3c19be21eaf42a6aaa7e2d04f23) (2026-10-14) and v2.1.7, RocksDB [v11.8.1](https://github.com/facebook/rocksdb/tree/v11.8.1). Written against rock-solid `86c47be`.

- **Workload.** An index of K live keys, each flush n uniform random updates of existing keys, as the chunk index gets from user writes and the cleaner's moves. Sequences, 2,000 flushes (200 for the real engines), measured over the second half: **steady** (every flush small), **alternating** (small, large, small, ...: the cleaner streams spike's S4), **bursty** (large with probability 0.2) and **log-uniform** (sizes spread evenly in log scale from a tenth of small to large). At the S4 scale the index is 44 MB of 40 B entries, a small flush 1.3 MB (64 MiB of 4 KiB writes at 2.06 index entries each) and a large one 33 MB (a cleaner pass, 25 times that). Two more scales: a 1.6 GB index (a MetaStore shard) with the same flushes, and the whole-chunk chunk index of the [LSM runs spike](../lsm-runs/), 30 MB with flushes of 40 and 1,000 entries.
- **Size model** ([model.go](model.go)). A run is the fraction of the key space it covers: a flush of n entries covers 1 − e^(−n/K), a merge the union 1 − ∏(1 − cᵢ). Bytes written count a compaction's output only if it survives to the next checkpoint, as `internal/lsm` writes it (an output merged again before then is never written).
- **Policies.** (a) **bucket**: a line-for-line port of `internal/lsm/compact.go`. (a′) bucket with RocksDB's fallbacks: when no bucket is due and the run count passes a cap, universal's size-ratio pick, else merge the newest runs − cap + 1. (b) **universal**: a port of `UniversalCompactionBuilder::PickCompaction` ([compaction_picker_universal.cc:767](https://github.com/facebook/rocksdb/blob/v11.8.1/db/compaction/compaction_picker_universal.cc#L767)): nothing below `level0_file_num_compaction_trigger` runs; size amplification (all runs but the oldest against the oldest, `max_size_amplification_percent` 200); size ratio from the newest run (`size_ratio` 1%, `min_merge_width` 2, `max_merge_width` unlimited, stop style total size); then the read-amplification fallback that merges the newest runs − limit + 1 whatever their sizes, the limit being the trigger or, with `max_read_amp` 0, auto-tuned from the largest run and a write-buffer size. (c) **Pebble v2.1.7 leveled**, driven for real ([pebble.go](pebble.go)): one batch and one `Flush` per checkpoint into an in-memory filesystem, no WAL, no compression, no filters, one compaction at a time and a wait for compactions to settle before the next flush; `LBaseMaxBytes` 64 MiB (default) and 4 MiB (the shape of a tree 16 times larger); read amplification is `Metrics.ReadAmp()`, L0 sublevels plus non-empty levels.
- **Validation** ([real.go](real.go)). The real `internal/lsm` (module `replace`) replays the same sequences with 16 B keys and 384 B values, the same bytes in a tenth of the entries: puts, a checkpoint per flush, then every compaction `PickCompaction` offers.

```
./fetch.sh        # optional: the cited sources at the pinned refs, into vendor/
./run.sh          # results-model.txt (instant), results-real.txt (1 min), results-pebble.txt (about 15 min)
```

Expected before the run: the bucket rule fails only under strict alternation; universal bounds the run count under every sequence at more bytes rewritten; Pebble keeps the fewest runs and rewrites the most.

## Findings per engine

## Conclusions

1. **The bucket rule cannot stay**: over runs adjacent in age it merges only while flush sizes are steady. It left a run per flush under alternating, bursty and log-uniform sizes alike (M1), in the size model and in the real `internal/lsm` (V1), so the S4 failure is the general case, not an edge.
2. **Adopt RocksDB's universal picker as it is**: size amplification first (200%), then size ratio (1%, at least 2 runs, no maximum), then the read-amplification fallback, with `max_read_amp` auto-tuned from a 1 MiB buffer. Across every sequence and scale it kept 2.3 to 6.7 runs on average and at most 2 + log2(largest run ÷ 1 MiB) (8 at 44 MB, 13 at 1.6 GB, 16 at 16 GiB), with WA 2.3 to 6.3 (9 to 27 on the whole-chunk index's tiny flushes, 0.4% of the log's bytes) and space 1.3 to 1.7 mean. Against the bucket rule on its one good case (steady) it keeps fewer runs (4.0 against 6.5) at 30% more bytes rewritten, and a third less space, which is memory as well since runs are held in memory.
3. **A fixed run limit is a knob, not the default**: four runs cost 100× the flushed bytes on a 1.6 GB index (M2), eight cost 4 to 7×. An index that must bound lookups without Bloom filters can set `max_read_amp` N; the run count then stays at N.
4. **Entries need no sequence number**: universal merges only adjacent runs, and the run's sequence number already orders them. RocksDB and Pebble use per-entry sequence numbers for snapshots and to order overlapping L0 tables, not for universal merges; a key-range slice of adjacent runs (incremental universal) needs none either.
5. **Leveled compaction is not for in-memory runs yet**: Pebble kept 1.5 to 3.5 runs but rewrote 2.8 to 17.7× (P1), and its key-range compactions replace pieces of a level one at a time, where our runs die whole in the metadata stream and cost the cleaner nothing. It is the shape to weigh again when indexes are read from disk and each run costs a read.
6. **Every policy's largest merge writes the whole index** (largest output 1.0× live, peak 3.1 to 4.5× live for universal): the reserve, or incremental universal's key-range slices, must cover it.
